# 设置与偏好 — Settings & Preferences

> **立场：设置页是「例外清单」，不是「功能目录」。** 默认值承担绝大多数人的体验，设置只承接「默认值确实服务不到的那一小部分」。判断顺序恒定：能不能不做（自动获取 / 跟随系统）→ 能不能就地做（任务内）→ 才轮到设置页。
> 适用：设置页、偏好面板、账号选项、通知开关矩阵、后台配置项。不适用：任务内筛选排序（就地控件）、首启该问什么（`onboarding-first-run.md` §5）。
> 快照 2026-11-23。来源全为一手官方文档；GNOME 页是 2024-10-23 的归档草案，只作旁证，不作唯一依据。

## §1 判层：四问决定「要不要成为设置」

1. **能自动获取或跟随系统吗？** 深浅色、语言、输入设备、手柄都能探到。用设置去索取这些信息，代价是出现两处事实源：用户会以为系统设置对它不生效，冲突时没人知道以谁为准（Apple HIG Settings 明确要求不要这样做）。
2. **是任务内临时选择，还是跨会话稳定偏好？** 前者就地做（显示/隐藏、排序、筛选），后者才进设置。任务选项搬进设置页的代价是脱离上下文，改完要「回来才看见结果」（Apple HIG）。
3. **会改的人占多少？** 少数人才改的，不要做成设置项，直接把默认做好（Apple：「为最多人提供最好的默认」）。
4. **改完要不要立刻看到结果？** 要 → 就地做 + 即时预览；只能在设置页盲改的（字号、主题），必须给示例。

| 场景 | 去处 | 判据 |
|---|---|---|
| 深浅色、语言、字号缩放 | 跟随系统，顶多「跟随/强制」三态 | 系统已有单一事实源 |
| 表格显示哪些列、排序 | 就地（表格工具栏） | 与当前任务绑定，换任务就变 |
| 通知类别开关 | 设置页偏好区 | 跨会话、跨页面，通道矩阵见 `notifications-messaging.md` §11 |
| 账号、安全、隐私 | 设置页顶层分组 | 低频、含法定义务，见 `design-ethics-inclusion.md` §6 |
| 单次导出格式 | 就地对话框 | 只对这一次有效 |
| 主题色、品牌皮肤 | 设置页 + 组织级默认 | 多租户见 `multi-brand-theming.md` |

**边界**：IDE、剪辑、CAD 这类专业工具，设置上百项合理，但必须配搜索、分组、可恢复默认。消费级产品超过 20 项，先怀疑是不是把「功能入口」塞进了设置页。

## §2 数量预算：5 是上限，不是目标

- **总设置条目 ≤5**（Microsoft 官方原文「keep the total number of settings to four or five」）。超过就分层：高频留主页面，低频收进 `SettingsExpander`，**嵌套不超过一层**。
- Apple 同向：设置太多会让产品「不好接近」，也让某一个具体设置更难找到。
- **反例**：8 个通知类别 × 3 个通道摊成 24 个开关。应聚成「类别 × 通道」矩阵，或给「全部 / 仅重要 / 自定义」三档预设。
- **代价**：每多一个设置，用户多一次「我该选哪个」的决定；没有推荐默认的设置，等于把设计责任推给用户。
- **边界**：法律要求的同意项（营销、Cookie、数据共享）不计入 5 条预算，但必须与功能设置分区，且默认关闭。

## §3 页面结构：单列、分组、可回退

- **单列自上而下**，分组用 section header，不做多列瀑布（Microsoft：single column）。
- 内容区最大宽度约 1000–1100 px（Windows 口径），更宽则行长过长、扫读变慢；移动端满宽 + 16 px 边距。
- 标题用名词，不加「设置」后缀：`Accounts` 而非 `Account settings`（Microsoft）。
- 底部固定 About 段：应用名、图标、版本 + 仓库、问题反馈、依赖许可、法务链接（Microsoft）。版本号可点击复制，省一次跳转。
- 入口唯一且符合平台肌肉记忆：macOS 放 App 菜单 Settings…（⌘,），**不放**窗口工具栏；Windows 用 NavigationView 末项并固定底部（`IsSettingsVisible`），命令栏场景放溢出菜单末位；watchOS 不设自定义设置页，必要项放主视图底部。
- 桌面窗口三条纪律（Apple HIG）：禁用最小化/最大化；标题随当前 pane 变；重开恢复上次 pane。理由一致——设置不是工作区，窗口状态不该被当作文档状态。
- 即时生效的页面不要「保存」；用 Cancel/OK 收尾时，Cancel 必须真的回滚（GNOME：instant-apply 窗口以 Cancel/OK 结束）。

## §4 控件映射：一个设置只用一种控件

| 设置类型 | 控件 | 阈值与边界 |
|---|---|---|
| 开/关 | toggle switch（原生 checkbox 亦可） | **标签在状态变化时不得改变**（APG Switch）；反例：开=「启用通知」、关=「禁用通知」 |
| 2–5 个互斥选项 | radio | Microsoft：从**最多 5 个**相关互斥项中选一个用 radio；超过 5 个改下拉或分段控件 |
| 6+ 互斥选项 | select / combobox | 需可搜索时用 combobox，契约见 `content-findability.md` §6 |
| 有安全区间的数值 | stepper/slider + 可直接输入 | 滑块必须显示当前值；无刻度滑块不给 |
| 多选并列 | checkbox group | 语义是「包含哪些」时用 checkbox（APG：switch 只有二值） |
| 依赖前项 | 缩进 + 禁用态 + 说明原因 | 不适用时禁用并说明为什么（Microsoft），不要直接隐藏 |

可访问性（APG 硬要求）：`role="switch"` + `aria-checked`；可见 label 或 `aria-labelledby`；成组用 `role="group"` + `aria-labelledby`（或 fieldset/legend）；说明挂 `aria-describedby`。Space 切换，Enter 可选。

## §5 生效模型：默认即时生效，Apply 是例外

- 默认 **instant apply**：改完立刻反映，不要「保存」按钮。
- **只有两种情况该用显式 Apply**：① 应用耗时超过约 1 秒；② 多项必须原子地一起应用，否则进入不稳定中间态（GNOME 原文例：hostname 与 proxy 必须同时生效）。
- 只影响少数控件的，把这几项分组、组内自带 Apply，其余仍旧即时（GNOME 原文）。
- 校验时机：**不要每次按键都校验**；在焦点离开控件或关窗时校验。例外是定长输入（如 hex 色值），输满即校验。
- **反例**：页面底部一个「保存」，但通知开关又立即生效——同一页两种模型，用户永远不知道哪些已经生效。
- **代价**：即时生效意味着没有「取消」，所以破坏性设置（清除数据、切换账号、重置）必须二次确认 + 写清后果，不能借即时生效省掉确认。

## §6 文案：说「控制什么」，不说「设置什么」

- 标签写对象：`消息通知` 而不是 `通知设置`；帮助写效果：`开启后会收到评论与 @ 提及`。
- 关闭态 = 什么都不发生，不要双重否定：关闭项里写「关闭后不会收到通知」要多读一遍才懂。
- 状态与动作分开：开关 label 是名词短语，开/关由控件表达，不要拿「开启/关闭」当 label。
- 给直达入口，不给路径说明：`[前往系统设置 →]` 优于 `设置 > 通知 > 允许通知`，后者会随系统版本失效。
- 四个文案口径同 `ux-writing.md` §6，本节只补设置页特有的「对象/效果」二分。

## §7 交付前判型清单（10 条，逐条可答）

1. 为什么不能自动获取或跟随系统？
2. 为什么不能就地做？
3. 总条目数多少？超 5 的部分凭什么留下？
4. 每项的默认值是什么？依据是什么？
5. 每项用哪种控件？二元项标签会随状态变吗？
6. 即时生效还是 Apply？若 Apply，满足 >1s 还是原子应用？
7. 校验在什么时机？有没有按键即红？
8. 关闭态文案能一遍读懂吗？
9. 入口在平台哪个位置？符合肌肉记忆吗？
10. 依赖项不适用时，是禁用 + 说明，还是消失？

- W3C WAI-ARIA APG Switch（w3.org/WAI/ARIA/apg/patterns/switch/）：二值、标签不变、role/aria-checked/group/describedby。
