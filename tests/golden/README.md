# Golden 评估集

## 为什么需要它

`scripts/audit.py` 能证明「统计口径一致、引用可解析、生成物不过期」，但证明不了
「设计产出的质量真的变好了」。过去几轮升级都出现过**自检 PASS 但内容退步**：
检查项全绿，实际产出却更模板化、更难用。这个目录用「固定 brief + 盲评」把
主观质量变成可比较的记录，防止自检分数代替质量判断。

## 怎么用

1. 取一份 brief（`01-…` 到 `14-…`），把「任务 / 用户 / 硬约束 / 三问」原样交给
   被测对象（人或 agent），不透露 brief 编号、不暗示答案。
2. 同一 brief 产出**两案**（A/B）：一版来自当前 SKILL.md，一版来自对照基线
   （上一版或人工参考稿）。两案使用同一份素材与同一套约束。
3. 按 [`rubric.md`](rubric.md) 做**盲评**：去掉品牌名、logo、落款、文件名等身份线索，
   由 ≥2 名评审独立打分。
4. 把逐轴分数、分歧与裁决理由记入 `baseline.md`（首次运行时新建；目前尚未建立）。
   后续每轮升级用同一 brief 重跑，与基线逐轴对比，而不是与「感觉」对比。

## brief 入选判据

一条 brief 能进这个目录，要同时满足四条；缺一条就别加——加了也测不出差异。

1. **有决策陷阱**：至少有一处硬约束与「默认做法」冲突（例：无图无表却要求术语可回查）。陷阱写在硬约束里，不写「注意别犯 X」——写出来被测对象会照抄提示。
2. **三问互相依赖**：后一问的答案受前一问约束，答错第一问会连带答错第三问；三个能独立回答的问题不构成一条 brief。
3. **期望命中 2–4 份资产**：1 份是查表题，5 份以上等于没有路由。
4. **无标准答案**：两个内行可以给出结构不同却都成立的方案。

反例：「做一个好看的落地页」——没有陷阱，两案都合格，分数只反映评审口味。代价：陷阱越隐蔽越考验 brief 质量，也越容易被评审读成「brief 没说清」；所以每条 brief 都要能指出陷阱落在哪条硬约束上。

- brief 里故意不写「预期分数」或「标准答案」，避免评估变成自证。

## 纪律

- brief 不随版本修改；确需修改时保留旧版并在 `baseline.md` 注明断点。
- 盲评材料里不得出现 `SKILL.md`、版本号、本目录路径等提示。
- 分歧 >1 分必须写理由（见 rubric 的强制裁决记录模板），不允许取平均了事。
- 评分表留空是刻意的：分数只能来自盲评现场，不能预填。
