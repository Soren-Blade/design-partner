# 设计交付与协作 / Design Handoff & Collaboration

> 快照 2026-11-01 · 取源：Carbon Component Checklist（definition of done 全表）、Carbon 2x Grid 与 Spacing（13 档 token 精确值）、Figma Dev Mode / Variants / Naming 官方文档、W3C DTCG Design Tokens Format 2025.10、Style Dictionary 文档、Semantic Versioning 2.0.0 全 11 条、Cucumber Gherkin 参考、NN/g Design Critiques、优设《设计走查流程》；工具 star/许可经 GitHub API 实测（2026-11-01）。

> 本文件解决一件事：**设计稿画完不等于交付完**。它给出"交什么、怎么标、怎么命名、怎么验、怎么改、怎么不返工"的可执行规则，而不是流程口号。

---

## 1. 一页速查：交付链的六个关卡

设计交付不是"发个链接"，是六次**信息交接**。每一次交接都会掉信息，掉的那部分最终会以返工的形式回来。

| 关卡 | 交付物 | 谁签字 | 掉信息的后果 | 详见 |
|---|---|---|---|---|
| ① 需求对齐 | brief + **验收标准 AC** | 产品 + 设计 | 方向做错，全量重画 | §8 §15 |
| ② 设计评审 | critique 记录 + 决策清单 | 设计负责人 | 上线后被"我觉得不好看"推翻 | §9 |
| ③ 规格交付 | **spec sheet + tokens** | 设计 → 开发 | 开发反推规则，偏差从第一个像素开始 | §3 §4 §13 |
| ④ 开发实现 | 组件 + Storybook story | 开发 | 偏差在复用中放大 | §7 §14 |
| ⑤ 设计走查 | 问题清单（P0–P3） | 设计 + 测试 | 上线"卸妆"，还原度崩 | §10 §11 |
| ⑥ 上线复盘 | 变更日志 + 债清单 | 全体 | 同一个错下次再犯 | §12 §17 |

**一句话立场**：**能写成规则的不要画成图，能写成 token 的不要写死数值。** 图和数值会过期，规则不会。

## 2. 交付的本质：交付决策，不是交付图

一张设计稿里其实有三层信息，交付时经常只传了最表面的一层：

| 层 | 内容 | 举例 | 开发能不能自己补出来 |
|---|---|---|---|
| **意图 intent** | 为什么这样设计、要解决什么 | "价格是决策核心，必须第一眼看到" | ❌ 补不出来 |
| **规则 rule** | 什么情况用什么 | "卡片间距 = 内容相关度：同组 8 / 跨组 24" | ⚠️ 只能猜 |
| **数值 value** | 具体 px / hex | "24px / #1677FF" | ✅ 能量出来 |

只给 value，开发就必须**反推** rule 和 intent——反推错了，你还得怪他"没还原"。

**交付完整度的判断法**：拿掉设计稿，开发只看文档能不能做出**第二个页面**。能，就是交付完了；不能，就还是"给了张图"。

**三件套**（缺一件就有一类问题必然发生）：

| 件 | 回答什么 | 形态 |
|---|---|---|
| **Spec sheet** | 规则是什么 | 表格 / 标注稿（§3） |
| **Prototype** | 行为是什么 | 可点原型 / 视频（§5） |
| **Tokens** | 数值从哪来 | JSON / CSS 变量（§13） |

## 3. 交付物清单：spec sheet 的 9 个字段

Carbon 把设计规格（design spec）定义为"开发用来在代码里构建组件、设计师用来在 Figma 里构建组件的**蓝图**，是视觉外观与功能的**唯一事实来源**"。它要求的六类内容，加上中文项目实际要的沟通字段，合成 9 项：

| # | 字段 | 必交 | 写什么 | 常见缺法 |
|---|---|---|---|---|
| 1 | **标识** | ✅ | 页面/组件名 + 版本号 + 状态（草稿/待评审/已冻结/已上线） | 只写"首页 v2"，不知道 v2 和 v3 差在哪 |
| 2 | **布局规则** | ✅ | 栅格、栏数、gutter、版心、断点 | 只给 1440 一稿 |
| 3 | **间距与尺寸** | ✅ | 只用 token 名 + 例外值；对齐关键线 | 全量标 px，没有 token |
| 4 | **字体与颜色** | ✅ | 只允许系统内 type token / color token | 出现 `#1677FF` 之外的野生色 |
| 5 | **交互状态** | ✅ | 9 态矩阵（§5） | 只画 default |
| 6 | **行为与边界** | ✅ | 响应式、溢出重排、展开收起、滚动、加载 | 数据放大 10 倍就崩 |
| 7 | **无障碍要求** | ✅ | 对比度、焦点顺序、标签与播报 | 走查时才发现焦点框没设计 |
| 8 | **素材与链接** | ✅ | 图标/插图源文件、组件库链接、原型链接 | 截图当素材 |
| 9 | **沟通字段** | ✅ | 对应开发、提测时间、验收人、变更记录 | 上线前找不到人 |

**Carbon 原文的六类要求**（可直接当验收口径）：

- **Color tokens**：规格里**只能**用系统内已有的 color token；**只能**包含已 token 化的颜色；用法要与其他应用一致。理由：token 是可复用性、可扩展性、无障碍与主题化的前提。
- **Type tokens**：同上，只允许已 token 化的字阶与字号。
- **Structure and measurements**：**只能用系统内的 spacing token**；**所有**元素的间距与对齐都要标注；**所有**可能的配置（尺寸、内容配置）都要覆盖。
- **Interaction states**：必须包含 hover、focus、selected、disabled、read-only、error、warning 等状态。
- **Behaviors**：必须包含响应式、内容溢出/重排、展开、滚动等行为。
- **Accessibility**：**所有文字颜色对背景 ≥4.5:1（disabled 态除外）**；**所有可交互非文本元素 ≥3:1**；**焦点流转必须写清楚**。

> 注意 Carbon 那句"**only**"出现了三次（only color tokens / only type tokens / only spacing tokens）。交付里的"只允许"比"建议使用"有用得多——前者可判定，后者不可判定。

## 4. 标注规则：标例外，不标全量

### 4.1 先把网格定死，标注量会掉一个数量级

Carbon 2x Grid 的硬数值（可直接抄）：

| 项 | 值 |
|---|---|
| **基础单位（mini unit）** | **8px 方格**；所有栏宽、行高、盒子、margin、padding 都是它的整数倍 |
| **padding** | **恒为 16px**（所有标准断点） |
| **gutter** | 两个相邻盒子 margin 各 16 → **合计 32px**；紧密相关内容可用**无 gutter** |
| **固定尺寸阶梯** | **8 / 16 / 24 / 32 / 48 / 64 / 80**（1x–10x） |
| **比例约束** | 盒子尺寸尽量落在 **1:1 / 2:1 / 2:3 / 3:2 / 4:3 / 16:9** |

Carbon 断点全表（**列数、单列占比、padding、margin 都有精确值**）：

| 断点 | px / rem | 列数 | 单列占比 | Size | Padding | Margin |
|---|---|---|---|---|---|---|
| Small | **320 / 20** | **4** | 25% | 80px | 16px | 0 |
| Medium | **672 / 42** | **8** | 12.5% | 80px | 16px | 16px |
| Large | **1056 / 66** | **16** | 6.25% | 64px | 16px | 16px |
| X-Large | **1312 / 82** | **16** | 6.25% | 80px | 16px | 16px |
| Max | **1584 / 99** | **16** | 6.25% | 96px | 16px | **24px** |

### 4.2 spacing token 13 档（Carbon 官方精确值）

| Token | rem | px | | Token | rem | px |
|---|---|---|---|---|---|---|
| `$spacing-01` | 0.125 | **2** | | `$spacing-08` | 2.5 | **40** |
| `$spacing-02` | 0.25 | **4** | | `$spacing-09` | 3 | **48** |
| `$spacing-03` | 0.5 | **8** | | `$spacing-10` | 4 | **64** |
| `$spacing-04` | 0.75 | **12** | | `$spacing-11` | 5 | **80** |
| `$spacing-05` | 1 | **16** | | `$spacing-12` | 6 | **96** |
| `$spacing-06` | 1.5 | **24** | | `$spacing-13` | 10 | **160** |
| `$spacing-07` | 2 | **32** | | | | |

Carbon 对"能不能用阶梯外的值"的回答是明确的：**"偏离 spacing 阶梯应尽可能避免"**。百分比（50% / 33%）可用于分栏与 max/min 宽度，但**不能当间距**。

**Carbon 还给了三条容易被忽略的标注纪律**：

1. **padding 里的文字要对齐到 padding 边缘，不能压在 padding 上**（`Always place type against the padding. Never place type on the padding.`）。
2. **Figma 的文本框默认带内边距**——标注前先检查并清掉，否则你标的 16px 实际渲染成 16+默认值。
3. **spacing token 本身不随断点变**，但允许**在断点处跳档**（1440 用 `$spacing-05`，768 用 `$spacing-03`）。这是"响应式间距"的正确写法，不是给每个断点造一套新数值。

### 4.3 只标这四类，其余靠 token 与网格

| 要标 | 为什么 |
|---|---|
| **① 例外值** | 不在 token 阶梯上的值必须标，并写原因（"设计稿 20px 是 24px 的视觉修正"） |
| **② 对齐关系（key line）** | 哪几个元素共用一条基线/一条左轴——这是开发最难从图上量出来的 |
| **③ 尺寸约束** | min/max 宽、固定宽、内容自适应规则（"名称列不截断，其余按比例分配"） |
| **④ 断点切换点** | 在哪个宽度、什么变了（§响应式五动词） |

**不要标**：每一条 8px 的间距、每个 padding、每个已经 token 化的圆角。全量标注的副作用是**开发看不见重点**——满屏红线等于没有红线。

### 4.4 单位换算写清楚

- 设计稿用 **px**，代码多用 **rem**；`1rem = 16px` 时 **24px = 1.5rem**、**8px = 0.5rem**。
- W3C DTCG 的 `dimension` 类型**只接受 `px` 和 `rem` 两个单位**，且 `value` 为 0 时 `unit` 仍必填。别在 token 里写 `em`/`vw`。
- 移动端 iOS 用 pt、Android 用 dp，与 px **1:1 等价**（DTCG 原文：px 是理想化像素，等价 dp/pt）。

## 5. 状态矩阵：9 态，别画 2ⁿ

Carbon 列的交互态是 7 个：**hover / focus / selected / disabled / read-only / error / warning**。加上设计侧必须补的两个：

| # | 状态 | 必交 | 判定标准 | 最常漏的点 |
|---|---|---|---|---|
| 1 | **Default** | ✅ | 无交互、无数据 | — |
| 2 | **Hover** | ✅ | 指针悬停；触屏无此态 | 暗色下 hover 方向搞反（应**提亮**） |
| 3 | **Focus** | ✅ | 键盘聚焦，**只对键盘可见**（`:focus-visible`） | 直接不画，或画了但对比度 <3:1 |
| 4 | **Active / Pressed** | ✅ | 按下瞬间 | 只改颜色不改位移，点击"没手感" |
| 5 | **Selected** | ✅ | 多选中或被选中（列表/标签/表格行） | 与 hover 视觉几乎一样，分不清 |
| 6 | **Disabled** | ✅ | 不可操作 | 只用透明度降，暗色下等于消失 |
| 7 | **Read-only** | ⚠️ 有只读场景必交 | 可选中/可复制，不可改 | 与 disabled 混为一谈（**read-only 必须过 4.5:1**） |
| 8 | **Error** | ✅ | 校验失败 | 只变红不加图标（违反"不只靠颜色"） |
| 9 | **Loading** | ✅ | 数据未到 | 用 spinner 撑破布局，没留占位尺寸 |

**两个补充态**（本技能立场，非 Carbon 原文）：**Empty**（有容器无数据，见 `feedback-states.md` §5）与 **Partial**（部分失败）。这两个不进 spec，走查时必然被漏。

### 5.1 组合爆炸的控制

一个按钮 3 尺寸 × 2 类型 × 9 状态 = 54 个变体。**不要全画**，按下面三刀砍：

1. **只画主路径**：每个组件选 **1–3 条真实主路径**（如"主按钮·大·实心"），其余尺寸/类型只在 default 态出图。
2. **状态只画"视觉有差异"的**：如果 hover 与 active 只差 4% 亮度，画一个 + 写一行规则，不要出两张图。
3. **写规则代替出图**：`disabled = 文字 25% + 底色 4%`（Ant 数值）这类可推导的，写公式比画 9 张图有用。

**验收口径**：9 态里**每一态都能在设计稿或规则表里找到出处**。找不到出处的，就是走查时会被打回的那一条。

### 5.2 disabled 的对比度例外，别用错地方

Carbon 明确写了 **4.5:1 "with the exceptions of disabled states"**。这条例外**只给 disabled**——read-only、placeholder、辅助文字、暗色下的次级文字**都不适用**。把"看起来灰"的文案都归到 disabled 是中文项目最常见的合规漏洞。

## 6. 命名四套：图层 / 组件 / 变体 / token

命名的唯一标准：**能不能不打开文件就找到它**。

### 6.1 Figma 的斜杠规则（官方机制，不是审美）

- 组件名里**每个 `/` 生成一级层级**：`Button/Primary/Large` → 资产面板里 `Button > Primary > Large`。
- 把已有组件合并成变体时，名字必须是 `componentName/property1value/property2value/...`；**第一个 `/` 之前是组件集名**，后面每个 `/` 生成一个属性。
  - `Button/Primary/Large/Default/False` → 组件集 `Button`，属性值 `Primary`、`Large`、`Default`、`False`。
- **每个被合并的组件斜杠数量必须相同**，否则值对不上属性，报 `corrupted variant`。
- **同一组合必须唯一**：两个变体的属性值完全一样就报冲突，哪怕视觉不同。
- **默认变体 = 组件集左上角那个**，它代表整个组件集出现在资产面板里。**所以左上角必须放最常用的那一版**，不是最漂亮的那版。
- 组件集**只能装组件**——不能放文字、标注、嵌套 frame、也不能只装一部分变体。

### 6.2 四套命名规则

| 层 | 规则 | 正例 | 反例 |
|---|---|---|---|
| **图层** | 语义 + 类型后缀；`Frame 12`/`Group 34` 一律清零 | `card / header`、`list / row / checkbox` | `Frame 214`、`Rectangle 8`、`副本 3` |
| **组件** | 类别在前、修饰在后；斜杠分级 ≤4 层 | `Input/Text/Default`、`Nav/Sidebar/Item` | `input2_new`、`按钮-大-蓝色` |
| **变体属性** | **语义名，不写视觉名**；值与代码 props 同名 | `type=primary/secondary`、`size=sm/md/lg`、`state=default/hover` | `color=蓝色`、`style=好看版`、`Variant2` |
| **token** | CTI：`category-type-item`，全小写、连字符 | `color-background-button-danger` | `btnRed`、`color1`、`zhuSe` |

### 6.3 为什么"红色"是坏名字

`color=red` 把**实现**写进了**语义**。品牌换成紫色那天，`red` 变成谎言，而且所有调用点都要改。正确写法是 `type=danger`，颜色由 token 决定。同理：`size=big` → `size=lg`（与代码 prop 对齐）、`style=round` → `shape=pill`（描述形状而非"圆角多少"）。

**判断法**：这个名字在**换肤/换品牌/换尺寸体系**后还成立吗？成立就留，不成立就改。

### 6.4 token 的 CTI 结构

Style Dictionary 推荐的 `Category / Type / Item` 三层（非强制，但用了就不会出现"到底叫 `button_color_error` 还是 `error_button_color`"的争论）：

```
color  →  background  →  button-danger
size   →  font        →  base / large
```

好处：`attribute/cti` 转换可以按路径自动给 token 打标签，之后**按标签过滤**（"只导出 color 类到 CSS 变量"）。命名一致性是**可编程**的副产品，不是靠人记。

### 6.5 中文项目的命名纪律

- **图层与组件名统一英文**，中文只出现在**文案内容**与**注释**里。混写会导致：搜索失效、导出文件名乱码、Figma 插件解析失败。
- 拼音命名（`zhuceye`）比中文更糟——既不是英文也不是中文，谁都搜不到。
- 设计稿文件名：`产品_页面_模块_v主.次_日期`，如 `shop_cart_list_v1.2_20261101`。**禁止 `final` / `最终版` / `最终版2` / `打死不改`**——这三个词出现即说明版本管理失效。

## 7. 组件 API 与设计稿 1:1 对齐

设计属性与代码 props 必须是**同一套词表**，否则每次交付都要做一次人工翻译。

### 7.1 Figma 的四类组件属性

| 属性类型 | 用途 | 命名建议 | 代码对应 |
|---|---|---|---|
| **Variant** | 多选一枚举 | `size` / `type` / `state` | union type / enum |
| **Boolean** | 有/无 | `isLoading` / `hasIcon` / `canClose` | `boolean` |
| **Text** | 可替换文案 | `label` / `title` | `string` |
| **Instance swap** | 换子组件 | `icon` / `leadingIcon` | `ReactNode` / slot |

**Boolean 命名用 `is/has/can/show` 前缀**，默认值取**最常见**的那个（通常是 `false`）。默认值错了，每个实例都要手动改一次。

### 7.2 属性数量的经验上限

Figma 官方没有上限，但**组合数是乘积**：3 属性 × 5 值 = 125 个变体，光是加载就会拖慢文件（官方明确：`Importing large component sets will impact Figma's speed and performance`）。

建议：**每个组件 3–5 个属性，每个属性 ≤5 个值**。超了就说明该拆组件，而不是加属性。拆法：把"内容区"抽成 instance swap，而不是给每种内容加一个 variant。

### 7.3 三条官方级禁令

1. **不要用变体分组不同图标**（Figma 原文："We don't recommend using variants to group different icons"）。同图标不同尺寸可以，不同图标不行——图标应该各自是组件，靠 `Icon/Name` 命名分类。
2. **组件集里不能放文字/标注/嵌套 frame**。要解释属性，把文字放在**组件集外面**，排成网格对齐。
3. **Dev resources 会传播到所有实例**。加到主组件上的 GitHub / Jira / Storybook 链接，所有实例都看得到——所以链接必须是**长期有效**的，不能指向临时分支。

### 7.4 Code Connect：让开发者看到"你的组件"而不是"自动生成的 div"

Dev Mode 默认给的是自动生成代码（可切语言与单位，CSS 单位可改）。接上 Code Connect 后，开发者看到的是**设计系统库里真实的组件代码**，变体与属性被映射到真实 props。

**什么时候值得接**：组件库 ≥20 个组件、有独立前端团队、组件 props 与设计属性已对齐。**什么时候不值得**：早期产品、组件还在周更、没有专人维护映射。

## 8. 验收标准的写法：Given / When / Then

走查之所以吵，是因为**没有事先写"该是什么样"**。AC（验收标准）就是那份"该是什么样"。

### 8.1 Gherkin 的三段语义（官方定义）

| 关键字 | 语义 | 纪律 |
|---|---|---|
| **Given** | 初始上下文，通常是**过去**已发生的事 | 只描述**状态**，不描述交互；可多个，第二个起用 `And` |
| **When** | 一个**事件/动作** | **单个**动作；不假设具体 UI 与技术 |
| **Then** | **可观测**的结果 | 只验用户/外部系统**看得见**的输出，**不查数据库** |

**官方硬建议**：每个场景 **3–5 步**；步数过多就失去"规格说明"的表达力。`Background` 复用重复前置，但**超过 4 行就该上提成更高层的步骤**。

### 8.2 设计 AC 的五条模板

```gherkin
场景：购物车删除最后一件商品
  Given 购物车中有 1 件商品，且用户已登录
  When 用户点击「删除」并确认
  Then 页面显示空态，标题为「购物车是空的」，并提供「去逛逛」主按钮
```

| 维度 | AC 句式 | 判定 |
|---|---|---|
| **视觉** | Given 在 1440 宽下，When 打开列表页，Then 表头/工具栏/分页与行高同为 47px，数字列右对齐 | 可量 |
| **状态** | Given 数据加载超过 2s，When 进入页面，Then 显示与真实布局同尺寸的骨架屏（不是 spinner） | 可看 |
| **交互** | Given 提交失败，When 用户返回表单，Then 已填内容完整保留，焦点落在第一个错误字段 | 可测 |
| **无障碍** | Given 只用键盘，When 按 Tab，Then 焦点依次经过 5 个可交互元素，焦点框 ≥2px 且对比 ≥3:1 | 可验 |
| **性能** | Given 4x CPU 降速 + 慢速 3G，When 首屏加载，Then LCP 元素在 2.5s 内可见 | 可测 |

### 8.3 三种写坏的 AC

| 坏法 | 例子 | 为什么坏 |
|---|---|---|
| **验内部** | `Then 数据库中有 1 条删除记录` | 用户看不见，删对了但页面没更新照样是 bug |
| **复合动作** | `When 用户填写表单并提交并刷新页面` | 三步合一，失败时分不清哪步错 |
| **不可判定** | `Then 页面美观、体验流畅` | 无法验收，等于没写 |

## 9. 设计评审（critique）：30 分钟，2 正 1 改

### 9.1 先分清两种"评审"

NN/g 明确区分：

| | **Standalone critique** | **Design review** |
|---|---|---|
| 目的 | 改进这份作品 | 按既定标准判定、决定是否放行 |
| 依据 | 设计目标与用户需求 | 启发式规则 / 设计规范 |
| 时机 | 任何阶段，可多轮 | 创意过程末尾 |
| 谁主导 | 同伴（facilitator 轮换） | 评审方（负责人/评审委员会） |
| 输出 | 改进项 | 通过 / 有条件通过 / 打回 |

**把两者混在一个会里，结果是"既没改进也没结论"。** 中文团队最常见的失败：名为评审会，实为领导拍板会，同伴不敢提问题，最后只剩"再改改"。

### 9.2 有效评审的三个前提（NN/g 原文三主题）

1. **范围清晰**：这次评什么、不评什么，必须写死。范围不清的评审 100% 会跑偏。
2. **目标一致**：先对齐"要解决什么问题、给谁解决"。没有共识的目标，任何反馈都是主观的。
3. **对话而非指令**：`I would have done it differently` 是评审杀手。

### 9.3 两种主持方法

| 方法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **Round robin** | 依次发言，绕桌一圈 | 人人有份、显得民主、可随机起点 | 话少的人容易说"我同意前面" |
| **Quotas** | 每人必须给**固定数量**的正/负反馈，如 **2 条做得好 + 1 条可改进** | 强制产出、避免只批评 | 只适合**破冰**，之后应转为自由讨论 |

### 9.4 角色与节奏

- **Presenter**：讲目标 → 讲故事（遇到什么问题、为什么这么决策）→ **明确提出想要哪类反馈**。**快速讲完**，别为每个决策辩护——辩解会吃掉真正讨论的时间。
- **Critiquer**：跨职能（含开发、测试、运营）。开发早进场能在"改起来还便宜"的时候提可行性。
- **Facilitator**：**每轮轮换**（防止一人长期主导、也给内向成员练手）。职责：定范围、发议程、控时间、把"太红了"翻译成目标问题、记录、跟进。
- **Recorder**：公开记（协作文档），允许所有人实时补充。

**节奏建议**（NN/g 的起步方案）：**每周 30 分钟**，round robin 评一个人正在做的项目。**"尽早开始、从小开始"**——不要等下一个大项目。

### 9.5 把意见翻译成问题（reframing）

| 原始反馈 | 翻译后 |
|---|---|
| "这布局太糟了" | "这个布局怎么帮用户更快完成任务？" |
| "我喜欢这配色，但按钮位置不对，整页很乱" | "如果目标是让用户快速注册，我担心我们把强调给了次要元素，主按钮反而不容易找到" |

**规则**：所有反馈必须**挂在目标上**。挂不上目标的，是个人偏好，记录但不执行。

### 9.6 五个坑（NN/g 原文）

1. 事先没对齐人物画像/目标
2. 会开太长
3. 把反馈当人身攻击
4. **当场急着解决问题**（评审是发现问题，不是现场改稿）
5. 只谈负面

**补一个中文特色坑**：**没有结论**。评审会开完没人知道"改不改、谁改、什么时候改完"。议程里必须留最后 5 分钟产出：`决策 / 待定 / 负责人 / 期限`。

## 10. 设计走查（design QA）：三遍法 + 9 字段文档

### 10.1 定义与边界

设计走查（又叫**还原度检查、视觉 Review、设计验证**）的目的是**保证落地效果与设计稿一致**。它在开发完成后的**测试阶段**进行，是上线前最后一道质检。

**必须和"体验走查"分开**：

| | 设计走查 | 体验走查 |
|---|---|---|
| 阶段 | 开发完成后的测试阶段 | **贯穿整个产品生命周期** |
| 焦点 | **还原度**（细节是否一致） | 易用性、一致性、美观性（更高维） |
| 依据 | 设计稿 + spec + AC | 设计法则 + 用户行为数据 |
| 输出 | 偏差清单（可修） | 体验问题与机会（可能改需求） |

**把体验问题塞进设计走查，会让走查清单无限膨胀、P0 被淹没。**

### 10.2 时机

- **在计划提测时间介入**：测试同学跑完第一遍流程后开始走查——太早页面还在动，太晚改不动。
- 开发反馈延期时，**先问产品原因、再评估是否影响设计**，不要自己干等。
- 走查通常占项目**约四分之一**的时间（优设原文口径）。这个比例要写进排期，不能当成"顺手看一眼"。

### 10.3 三遍法：先大后小，先流程后像素

| 遍 | 查什么 | 怎么查 | 产出 |
|---|---|---|---|
| **第一遍 · 业务流程** | 主流程能否走通 | 把自己当第一次用的用户，从进入到完成完整走一遍 | 流程级阻断（多为 P0） |
| **第二遍 · 交互** | 与交互说明逐条对照 | 拿交互说明/AC **一条一条打勾**，含异常态、边界态 | 交互偏差（P1） |
| **第三遍 · 视觉** | 色彩/字体/布局/间距/图标 | 叠图比对、量关键值、过一遍 §5 九态 | 视觉偏差（P1–P3） |

**为什么不能先抠像素**：先抠像素会让你在一条本来就走不通的流程上纠结 2px，而真正的阻断问题排在清单末尾。

### 10.4 走查文档的 9 个字段

| # | 字段 | 要求 |
|---|---|---|
| 1 | **功能模块** | 页面 + 区块，能定位 |
| 2 | **设备环境** | 机型 / 系统版本 / 分辨率 / 浏览器 / 缩放比例 / 字体 |
| 3 | **问题描述** | 现象 + **正确值**（"按钮应为 `#E74957`，实际 `#E74C3C`"） |
| 4 | **问题截图** | 带标注的截图，不是原图 |
| 5 | **对应设计稿** | 链接 + 具体 frame 名（不是"看设计稿"） |
| 6 | **优先级** | P0–P3（§11） |
| 7 | **对应开发** | 人名，不是"前端" |
| 8 | **处理状态** | 待处理 / 已修待验 / 已关闭 / 不修复（附理由） |
| 9 | **验收结果** | 复查人 + 日期 + 结论 |

**一条一问题**。把 5 个问题写进一行，结果一定是修了 3 个、漏了 2 个、还吵了一架。

### 10.5 沟通纪律

1. **邮件/文档正式发出**：正式渠道提高重视度，也留痕（原文："防止日后被甩锅"）。
2. **当面澄清一次**：把清单过一遍，确认理解一致，比在群里来回打字快得多。
3. **约定修复完成时间**，写进清单。
4. **复查并记录**：只验 P0/P1 的实际效果，P2/P3 可抽样；每条都要有"已关闭"的痕迹。

### 10.6 走查环境的六个变量（缺一个就会吵）

机型 / 系统版本 / 屏幕分辨率 / 浏览器与版本 / **系统缩放或字体大小** / 是否暗色模式。

**最常见的假 bug**：设计师在 100% 缩放下量出 47px，开发在 125% 缩放下量出 58.75px。先对齐缩放，再谈像素。

## 11. 缺陷分级与发布门禁

分级只看一件事：**用户还能不能完成他的目标**。不看"改起来多贵"，也不看"谁写的"。

| 级别 | 定义 | 例子 | 门禁 |
|---|---|---|---|
| **P0 阻断** | 主流程走不通 / 数据丢失 / 无障碍阻断 / 品牌事故 | 支付按钮点不动；删除后列表不刷新；焦点完全不可见；错误 logo 上线 | **必须为 0 才可上线** |
| **P1 严重** | 主流程视觉或交互错误、关键状态缺失 | 表单错误提示不出现；表格数字列左对齐；空态缺失；对比度不达标 | 需**书面豁免**（谁批、何时补） |
| **P2 一般** | 非主流程偏差、token 未使用、间距错档 | 二级页标题字号差 2px；用了 `#1677FF` 而非 token | 进 backlog，**下个迭代清零** |
| **P3 轻微** | 1–2px、文案标点、图标描边 | 逗号用了半角；图标 1.5px 而非 2px | 批量修，可合并发布 |

**三条分级纪律**：

1. **P0 不接受"下个版本修"**。上线即事故。
2. **P1 的豁免必须写清"谁批的、什么时候补"**，否则等于默认降级成 P3。
3. **P2 不清零会变成永久债**。建议每个迭代固定留 10% 工时还设计债。

## 12. 版本与变更管理

### 12.1 SemVer 2.0.0 的 11 条（设计系统直接照搬）

| 规则 | 内容（要点） |
|---|---|
| 1 | 用 SemVer 就**必须声明公共 API**（写在代码或文档里），且要精确、完整 |
| 2 | 版本形如 `X.Y.Z`，非负整数、**无前导零**，逐位递增（`1.9.0 → 1.10.0`） |
| 3 | **已发布版本的内容不可修改**，任何修改都必须发新版本 |
| 4 | `0.y.z` 是初始开发期，**任何东西都可能变**，API 不视为稳定 |
| 5 | `1.0.0` 定义公共 API，此后的递增规则以此为准 |
| 6 | **PATCH**：仅向后兼容的 bug 修复 |
| 7 | **MINOR**：向后兼容地新增功能；**标记任何功能为废弃也必须递增 MINOR**；MINOR 递增时 PATCH 归零 |
| 8 | **MAJOR**：任何不兼容变更；MAJOR 递增时 MINOR 与 PATCH 归零 |
| 9 | 预发布：`-` 后接点分标识符，仅 `[0-9A-Za-z-]`，数字标识符无前导零；优先级低于对应正式版 |
| 10 | 构建元数据：`+` 后接，**不参与优先级比较** |
| 11 | 优先级：major > minor > patch > 预发布；数字标识符按数值比，含字母的按 ASCII 比，**数字低于非数字**；前缀相同则字段多者更高 |

**废弃的正确姿势**（SemVer FAQ 原文要点）：① 更新文档告知；② **发一个带废弃声明的 MINOR**；③ 在下一个 MAJOR 里才彻底移除——**中间至少隔一个 MINOR**，让使用方平滑迁移。

### 12.2 映射到设计系统

| 变更 | 版本 | 例子 |
|---|---|---|
| 删除组件 / 重命名 token / 改默认值 / 改组件必填 props | **MAJOR** | `color-primary` → `color-brand`；Button 默认 `type` 从 primary 改 secondary |
| 新增组件 / 新增 token / 新增可选属性 / 新增尺寸 | **MINOR** | 新增 `Table/Compact`；新增 `$spacing-14` |
| 修视觉 bug / 修对比度 / 修图标路径 / 修文档错字 | **PATCH** | 按钮 hover 从 6% 改 8% 提亮 |

**"改默认值"是最容易被误判成 PATCH 的 MAJOR**。默认值一改，所有没显式传值的调用点视觉全变——这是不兼容变更。

### 12.3 变更日志格式（Keep a Changelog 六类）

`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`。每条写**影响面**，不只写"优化了按钮"：

```
## [2.0.0] - 2026-11-01
### Removed
- 移除 `Button type="ghost"`（影响 12 个页面，迁移方案见 codemod `v2-ghost-to-text`）
### Changed
- `$spacing-05` 由 16px 调整为 16px（无变化，仅文档澄清）
```

### 12.4 MAJOR 必须带 codemod

Carbon 的要求写得很直白：如果变更需要消费方迁移，就**必须提供自动化迁移脚本**（通过 `@carbon/upgrade` 发布）。理由是"迁移成本乘以所有团队，会显著影响整体产出"。

**设计侧对应物**：MAJOR 变更必须附一份**逐条替换表**（旧 token → 新 token，旧变体 → 新变体），让开发能脚本化替换，而不是靠人肉搜。

### 12.5 三个版本号不要混

| 版本 | 管什么 | 谁维护 |
|---|---|---|
| **设计稿版本** | 某个页面/流程的第几版 | 设计师 |
| **组件库版本** | 组件与 token 的 SemVer | 设计系统团队 |
| **产品版本** | 对外发布的版本 | 产品/发布 |

**事故高发点**：设计稿写"v3"，组件库已经到 2.4.0，产品是 5.1.2，三方对不上。交付文档里必须同时写清**三个版本号**。

## 13. Token 交付管线：从设计变量到代码

### 13.1 三层不要混（详见 `design-tokens.md`）

`base`（原始值）→ `semantic`（语义角色）→ `component`（组件覆盖）。**组件层只引用后两层，禁止硬编码**。Carbon 的原话是"组件样式**不得包含未 token 化的魔法数字或颜色**"。

### 13.2 W3C DTCG 格式（2025.10 草案）

⚠️ **重要前提**：官方明确标注这是**预览草稿**（Draft Community Group Report），"请勿直接据此实现"，它**既不是 W3C 标准，也不在标准轨道上**。用它做**交换格式**可以，用它做**合规承诺**不行。

| 项 | 规定 |
|---|---|
| **文件** | JSON（RFC8259）；扩展名 **`.tokens`** 或 **`.tokens.json`** |
| **MIME** | 优先 `application/design-tokens+json`，回退 `application/json`；工具必须两种都支持 |
| **token 识别** | 含 **`$value`** 的对象就是 token |
| **组识别** | **不含** `$value` 的对象是组 |
| **保留属性** | `$value`（必需）、`$type`、`$description`、`$extensions`、`$deprecated` |
| **名称禁令** | 不得以 `$` 开头，不得含 `{` `}` `.`（与别名语法冲突） |
| **类型继承** | 引用 → 取被引用者的类型；否则取**最近**带 `$type` 的父组；都没有则**该 token 无效**。**禁止靠值的内容猜类型** |
| **别名** | `{group.token}`（隐式指向 `$value`）与 JSON Pointer `$ref`（如 `#/colors/blue/$value`）**两种都必须支持** |
| **组继承** | `$extends: "{group}"`，深度合并：继承 → 同路径本地覆盖（整 token 替换，非逐属性）→ 新增 |
| **`$root`** | 组可用保留名 `$root` 提供基础值；路径为 `color.accent.$root`，直接引用组 `{color.accent}` **无效** |
| **必须报错** | 引用解析失败、`$extends` 指向非组、任何循环（别名/`$extends`/`$ref`）、语法畸形、类型不匹配、对象同时含 `$value` 与子级 |

**基础类型**：`color` / `dimension` / `fontFamily` / `fontWeight` / `duration` / `cubicBezier` / `number`。
**复合类型**：`strokeStyle` / `border` / `transition` / `shadow`。

两个易错点：
- `dimension` **只接受 `px` 与 `rem`**，且 `value: 0` 时 `unit` **仍必填**。
- `fontWeight` 预定义字符串是**有限集**：100 thin/hairline、200 extra-light/ultra-light、300 light、400 normal/regular/book、500 medium、600 semi-bold/demi-bold、700 bold、800 extra-bold/ultra-bold、900 black/heavy、950 extra-black/ultra-black。**超范围或大小写不符必须被拒绝**。

```json
{
  "color": {
    "$type": "color",
    "brand": { "$value": { "colorSpace": "srgb", "components": [0, 0.4, 0.8], "hex": "#0066cc" } },
    "action": { "$value": "{color.brand}" }
  },
  "space": {
    "$type": "dimension",
    "md": { "$value": { "value": 24, "unit": "px" } }
  }
}
```

### 13.3 Style Dictionary 的构建规则

| 规则 | 细节 |
|---|---|
| **两套格式不能混用** | 原生格式用 `value`/`type`/`comment`；DTCG 用 `$value`/`$type`/`$description`。**同一实例内只能选一套** |
| **合并顺序** | 先 `include`（按数组顺序）→ 再 `source`（按顺序）；**后加载的覆盖先加载的** |
| **冲突警告** | 两个 `source` 文件定义同名 token → 打印 **collision 警告**；`source` 覆盖 `include` → **不警告**（这是主题覆盖的正常用法） |
| **目录不影响结构** | 文件怎么分目录都行，最终**深度合并**成一棵树 |
| **自动元数据** | `name`（默认取 key）、`path`（数组路径）、`original`（纯净副本）、`filePath`、`isSource` |
| **别名语法** | `{size.font.medium}`；**只对 `value` 有效**，引用非 value 的字段会产出异常 |

**标准管线**：

```
Figma Variables / Tokens Studio
        ↓ 导出 .tokens.json（DTCG）
   tokens/base.json + semantic.json + component.json
        ↓ Style Dictionary（transformGroup + format）
  CSS 变量 / JS 常量 / SCSS / iOS Swift / Android XML
        ↓ 组件引用变量（禁硬编码）
     Storybook + 视觉回归
```

### 13.4 token 交付的五条纪律

1. **一个 token 一个用途**。`color-blue-500` 可以给多处用；`color-button-bg` 只能给按钮用。语义 token 被复用成"万能色"，改一次全站崩。
2. **不在组件里写死 hex**。Carbon 把"无未 token 化的魔法数字"直接列为交付要求。
3. **`$description` 要写"什么时候用"，不写"是什么"**。写 `"按钮正常态背景"` 比写 `"蓝色"` 有用。
4. **废弃用 `$deprecated`，不要直接删**。它支持 `true` / 字符串（写原因）/ `false`（覆盖组默认），字符串形式等于自带迁移提示。
5. **导出前跑校验**：命名合规、无循环引用、类型齐全、无重复路径。

## 14. 回归防线：让"改 A 崩 B"在合并前被发现

Carbon 的测试要求可以直接当行业基线：

| 层 | 要求 | 具体值 |

### 14.2 设计侧的"回归"：比代码更早

Figma Dev Mode 自带两种 diff，走查前先用它们自查：

- **Compare changes**：对比当前版本与历史版本（帧历史弹窗）。
- **Compare with main component**：实例 vs 主组件——**这是发现"某人本地改了一个实例"的最快方式**，也是"设计稿与组件库漂移"的检测器。

**纪律**：定稿前跑一次 `Compare with main component`。分离实例（detached）越多，说明组件库越不合用，这是组件库该迭代的信号，不是设计师该被批评的理由。

## 15. 协作节奏：每次交接都要有可验收的产出

```
需求确认 ──► 设计评审 ──► 规格冻结 ──► 提测 ──► 设计走查 ──► 上线 ──► 复盘
   │            │            │           │         │          │        │
  brief+AC   决策清单      spec+tokens  可点环境  问题清单  变更日志  债清单
```

| 节点 | 最小产出 | 判断"这一步做完了" |
|---|---|---|
| 需求确认 | brief 六要素 + **AC 五条** | 开发能说出"什么算做完" |
| 设计评审 | 决策 / 待定 / 负责人 / 期限 | 没有"再看看吧" |
| 规格冻结 | spec sheet + token 清单 + 原型 | 拿掉设计稿也能做出第二个页面 |
| 提测 | 可点环境 + 已知问题列表 | 设计能在真实环境点 |
| 设计走查 | 9 字段清单 + P0–P3 | P0 = 0 |
| 上线 | 变更日志（六类） | 能回答"这版改了什么" |
| 复盘 | 债清单 + 下轮预防项 | 有具体动作，不是"下次注意" |

### 15.1 冻结后要改怎么办

**变更单四问**（写不清就不改）：

1. **影响面**：影响几个页面 / 几个组件 / 是否影响已发布版本？
2. **工时**：设计 + 开发 + 测试各多少？
3. **是否延期**：延期就由提需求的人签字。
4. **是否进 MAJOR**：改 token 名/默认值 = MAJOR（§12.2）。

**没有变更单的口头改动，是交付失控的第一入口。**

### 15.2 异步优先

- 设计稿**提前发**（评审前至少半天），避免"现场第一次看"的直觉反应。
- 问题**写在文档**，群里只发通知与链接。
- 会议**只做决策**，不做信息同步（信息同步用文档）。

**中文现实**：微信群/企微群是最容易吞结论的地方。**规则：群里出现的任何结论，24 小时内必须回写文档**，否则视为没发生。

### 16.1 术语对齐表（对外沟通直接用）

| 中文口语 | 正式说法 | 对应本文件 |
|---|---|---|
| 提测 | 提交测试 | §10.2 |
| 走查 / 还原度检查 / 视觉 Review | 设计走查 | §10 |
| 过一遍 / 验收 | 设计验收 | §11 |

| 复盘 | 迭代复盘 | §15 |
| 甩锅 / 扯皮 | 责任边界不清 | §10.4 字段 7 |

### 16.2 交付包清单（对外/外包/甲方）

| 类别 | 内容 | 缺了会怎样 |
|---|---|---|
| **源文件** | Figma 链接（**可编辑权限**）或 Sketch/PSD 源文件 | 合作方永远改不动 |
| **规格** | spec sheet + token 表 | 每次改动都要问一次 |
| **素材** | 图标 SVG（转曲）、插图源文件、图片 @1x/2x/3x | 上线现补、糊 |
| **字体** | 字体文件 + **授权说明**（商用范围、可嵌入与否） | 侵权风险 |
| **规范** | DESIGN.md / 品牌手册 | 第二个页面开始漂移 |
| **清单** | 页面清单 + 状态清单 + 已知问题 | 验收范围扯皮 |

### 16.3 三份签字文件

1. **Spec**（该是什么样）
2. **走查表**（实际是什么样）
3. **变更记录**（过程中改了什么、谁批的）

**只有前两份，没有第三份**，是"上线后互相不认账"的根本原因。

### 16.4 合规口径（政府/金融/医疗/适老化项目）

- 无障碍常要求 **GB/T 37668 + WCAG 2.1/2.2 AA 双达标**（详见 `accessibility.md` §15）。
- 适老化项目另有工信部口径的 **60×60 / 48×48 / 44×44 dp** 与行距 ≥1.3。
- **验收前把口径写进合同/需求文档**。上线后再谈标准，只能返工。

### 16.5 三句可以直接用的话

| 场景 | 别说 | 说 |
|---|---|---|
| 还原度差 | "这不是我设计的" | "这里和 spec 差 8px（spec §3.2），改完我明天复查" |
| 需求中途改 | "又要改？" | "可以改。影响 3 个页面，约 1.5 天，是否顺延上线？" |
| 评审没结论 | "大家再想想" | "今天定 2 件、挂 1 件。挂起的那件周五前给结论，负责人是 X" |

## 17. 度量：交付质量的六个指标

**说明**：下面是**建议基线**（本技能立场），不是行业统计数据。目的是让"交付好不好"从感觉变成可讨论的数字。第一轮先测**自己的基线**，第二轮再谈改善。

| 指标 | 算法 | 建议基线 | 说明 |
|---|---|---|---|
| **走查问题密度** | 问题数 ÷ 页面数 | ≤5 条/页 | 超过说明 spec 不够或开发没看 spec |
| **一次通过率** | (P0+P1=0 的页面数) ÷ 总页面数 | ≥70% | 最直接反映交付质量 |
| **P0 数** | 上线前阻断问题数 | **0** | 非 0 不许上线 |
| **返工率** | 返工工时 ÷ 总设计工时 | ≤15% | 超过说明需求或评审失效 |
| **token 覆盖率** | 使用 token 的样式数 ÷ 总样式数 | ≥90% | 直接查"野生 hex"数量 |
| **变更影响面** | 受影响页面数 ÷ 总页面数 | 单次 MAJOR ≤30% | 超过说明抽象层没做好 |

**两个"过程指标"**（不需要工具，靠人记）：

- **spec 提问次数**：开发在实现期问"这里多少 px"的次数。**趋近 0 = spec 合格**。
- **重复问题数**：同一类问题在两次走查中都出现。**>0 说明复盘没落地**。

## 18. 反模式 20 条

1. **只交图不交规则**——开发反推，偏差从第一个像素开始。
2. **全量标注**——满屏红线，重点全丢。
3. **用截图当标注**——不能复制数值，不能查 token。
4. **只画 default 态**——hover/focus/disabled 全靠开发猜。
5. **组件集里塞文字说明**——Figma 根本不允许，硬塞就是散落的文本框。
6. **变体用视觉命名**（`红色`/`大号`）——换品牌那天全变谎言。
7. **默认变体放最漂亮那版**——资产面板里所有人拿到的都是错的那版。
8. **用变体分组不同图标**——官方明确不建议。
9. **一个组件 8 个属性**——组合爆炸，文件卡死。
10. **设计属性与代码 props 不同名**——每次交付都要人工翻译。
11. **没有 AC 就开始做**——验收时全靠"我觉得"。
12. **AC 写成"美观、流畅"**——不可判定，等于没写。
13. **评审会当场改稿**——时间全花在 2px 上，方向问题没人看。
14. **评审会没有结论**——开完没人知道改不改。
15. **走查从像素开始**——在走不通的流程上纠结 1px。
16. **走查一条写 5 个问题**——修 3 漏 2。
17. **P0 允许"下版修"**——上线即事故。
18. **改默认值当 PATCH 发**——所有调用点视觉突变，却不升 MAJOR。
19. **MAJOR 不带迁移表/codemod**——迁移成本乘上所有团队。
20. **三个版本号混着用**——设计稿 v3 / 组件库 2.4.0 / 产品 5.1.2，谁也说不清在交付哪一版。

## 19. 自检 20 项（交付前逐条打勾）

1. 拿掉设计稿，开发只看文档能做出**第二个页面**吗？
2. Spec 的 9 个字段齐了吗（标识/布局/间距/字体颜色/状态/行为/无障碍/素材/沟通）？
3. 颜色与字号**只用 token**，没有野生 hex 与野字号？
4. 间距**只用 spacing token**；例外值都标了**原因**？
5. 标注里只标了**例外值 / 对齐关系 / 尺寸约束 / 断点切换**，没有全量标？
6. 9 态（default/hover/focus/active/selected/disabled/read-only/error/loading）都有出处？
7. 只读（read-only）与禁用（disabled）**视觉可分**，且 read-only 过 4.5:1？
8. 行为规格写了响应式/溢出重排/展开/滚动/加载五类？
9. 图层名里**没有** `Frame 12` / `Group 34` / `副本`？
10. 组件名走 `类别/修饰`，变体属性是**语义名**不是视觉名？
11. 组件属性 **3–5 个**、每属性 ≤5 值，默认值是最常见那个？
12. 设计属性名 = 代码 props 名，开发者不需要翻译？
13. 每个主流程都有 **3–5 步**的 Given/When/Then，Then 是**可观测**的？
14. AC 覆盖了视觉/状态/交互/无障碍/性能五个维度？
15. 评审会有**决策/待定/负责人/期限**四项产出？
16. 走查是**三遍法**（流程→交互→视觉），不是从像素开始？
17. 走查表 9 字段齐全，**一条一问题**，每条带**正确值**？
18. 环境六变量（机型/系统/分辨率/浏览器/**缩放**/暗色）已对齐？
19. P0 = 0；P1 的豁免写了**谁批、何时补**？
20. 本次变更的**版本级别**（MAJOR/MINOR/PATCH）判定过，MAJOR 带了迁移表？
