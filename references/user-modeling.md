# 用户建模（User Modeling）


> 采集到的偏好如何晋升为规则见 `memory.py` 与 `profile.md`；比较方案时的五轴见 `taste-criteria.md` §8。
> 本文件回答一个问题：在动手设计之前，怎么把「用户」从一个词变成一组能改变设计动作的事实。
> 它是方法论，不是模板填空；配套的存储是 `memory/journal.jsonl`（原始信号）与 `memory/profile.md`（晋升后的规则）。

## §0 立场：画像不是人口统计学

画像不是「25–34 岁、一线城市、本科学历、喜欢简约风」。这些字段能写进投放后台，却无法回答设计会上的一句话：「这个按钮为什么要放这里？」

画像要写的是两件事：

1. **这个人在这个场景里怕什么**——怕多付钱、怕填错、怕被同事看见自己不会用、怕审计时拿不出凭证、怕点错之后无法撤回。
2. **他已经试过什么**——用过哪个竞品、在哪一步放弃、现在用什么 workaround 顶着、上次为什么骂人。

三条判据，缺一不成立：

| 判据 | 问法 | 不成立的样子 |
| --- | --- | --- |
| 能改变设计动作 | 读完这条，我会改哪个像素、哪句文案、哪个默认值？ | 「用户喜欢简洁」——改不动任何东西 |
| 能被证伪 | 什么观察结果会说明这条是错的？ | 「用户想要高级感」——怎么都算对 |
| 能追溯到证据 | 这条来自哪次会话、哪句原话、哪个任务？ | 「根据经验，用户通常……」 |

写不出「怕什么」和「试过什么」，就还没开始建模，只是在给人群贴标签。

## §1 画像五问

按顺序问，前一问答不出来，后一问的答案多半是编的。

### 1.1 谁：角色 + 处境，不是年龄性别

问法是「他在这件事里的位置是什么」，不是「他是什么人」。

- 合格：连锁餐饮的区域财务，月底要合并 12 家门店的发票，被总部审计追着要凭证。
- 合格：独立开发者，一边上班一边维护 side project，只在晚上十点后有空改落地页。
- 不合格：都市白领、Z 世代、宝妈、极客——这些词不指向任何具体决策。

角色要带三个限定：**职责**（要对什么结果负责）、**权限**（能改什么、不能改什么）、**被谁检查**（老板、审计、客户、公开舆论）。

### 1.2 在什么场景：触发时刻 + 环境约束

场景不是「使用 App 时」，是「什么时刻、在哪、手上有什么、旁边有谁」。

采集清单：

- 触发时刻：被什么事件推着打开（收到账单、被领导 @、客户催、系统报警）？
- 设备与网络：手机单手还是桌面双屏？地铁弱网还是办公室千兆？
- 时间压力：有 30 秒还是 30 分钟？能不能中断后再回来？
- 并行任务：是一次只做这一件事，还是一边开会一边填？
- 可见性：屏幕旁边有没有同事/客户在看？

同一个「导出报表」功能，在「月末财务批量导 300 张」和「老板临时要一张看一眼」是两个完全不同的场景，控件、默认值、错误提示都不同。

### 1.3 怕什么：损失的具体形态

把「怕」翻译成可计价的损失：

| 怕的类型 | 具体表现 | 设计上的后果 |
| --- | --- | --- |
| 怕多付钱 | 结账时冒出服务费、税费、汇率加价 | 总价前置、费用逐项、结账不再加价 |
| 怕填错 | 提交后发现税率/抬头错了，要红冲 | 提交前可核对、关键字段二次确认 |
| 怕丢数据 | 写了 40 分钟，刷新全没 | 自动保存、草稿恢复、离开拦截 |
| 怕出丑 | 不会用，被同事看着 | 可探索的默认值、随时可退、不惩罚试错 |
| 怕被追责 | 审计要凭证，拿不出来 | 留痕、版本、导出可复核 |
| 怕被操纵 | 默认勾选、取消入口藏起来 | 默认不勾选、拒绝与同意同样显著 |

怕什么，决定了「哪里必须多一步确认、哪里必须少一步点击」。这两件事都不能靠感觉，必须能指回一条具体损失。

### 1.4 已经试过什么：替代方案与失败点

用户不是空手来的。他大概率已经：

- 用过竞品或上一版，在某个具体步骤放弃；
- 用 Excel / 微信 / 截图 + 手工 顶着；
- 问过客服/同事，得到一个 workaround；
- 形成了一套自己的「土办法」（命名规则、文件夹结构、快捷短语）。

采集问句（按顺序）：

1. 「这件事你现在是怎么做的？」——拿流程，不拿评价。
2. 「上次卡在哪一步？」——拿失败点，越具体越好。
3. 「后来怎么绕过去的？」——拿 workaround，它往往就是最好的需求文档。
4. 「为什么不继续用 XX？」——拿竞品的真实死因，不是评分。

已经试过什么，直接决定首屏该不该做教育：用户从竞品迁移过来时，最想看的是「你和它有啥不一样」，不是「什么是发票」。

### 1.5 审美基线：参照物，不是形容词

不要问「你喜欢什么风格」，要问「这几个里面哪个更接近」。参照物可以是：

- 5 张同类产品的截图（§4 详述）；
- 他现在的网站/文档/PPT；
- 他佩服的一家公司的官网；
- 他明确讨厌的一个案例（负参照同样有效）。

审美基线只回答三件事：**信息密度**（稀疏还是密集）、**语气**（克制还是热情）、**材质**（扁平、纸质、还是带光影）。其余都可以从这三件事推。

## §2 场景切片法

「用户」是一个集合名词，直接对它做设计，得到的一定是 average user——一个不存在的、什么都占一点的人。切片法把它拆成 3 个具体的人：

| 切片 | 定义 | 作用 |
| --- | --- | --- |
| 主切片 | 占流量/收入 60–70% 的那一类，当前版本首要服务对象 | 决定默认路径 |
| 边缘切片 | 用量小但流失代价高（无障碍用户、超大批量用户、弱网用户） | 决定边界与降级 |
| 对抗切片 | 最不配合、最容易误用的人（恶意用户、赶时间乱点的人、审阅者） | 决定防错与安全 |

每个切片必须产出一条**可验证假设**，格式固定：

> 如果〈设计动作〉，那么〈切片〉在〈场景〉下会〈可观察的行为变化〉；验证方式：〈5 分钟任务测试 / 埋点 / 访谈问句〉。

示例（B2B 发票工具）：

- 主切片（区域财务，月末批量）：如果默认按「待开票 → 已开票」分组并支持批量红冲预览，那么她在 300 张的场景下会减少一次导出核对；验证：任务测试里统计导出次数。
- 边缘切片（读屏用户）：如果金额脊柱的每个数字都有可读的列名关联，那么读屏用户在核对五个数时不会串行；验证：NVDA 走查一遍对账任务。
- 对抗切片（赶时间的采购）：如果在提交前显示「本单将占用预算 ¥X，剩余 ¥Y」，那么他会减少提交后撤回；验证：撤回率埋点。

三条纪律：

1. 每片只写一个人，不写「这类用户通常」；
2. 假设必须能被一次观察推翻，否则重写；
3. 切片会随证据变化，变了就改，不要维护一份体面的旧画像。

## §3 禁忌清单模板

禁忌是画像里最值钱的部分：偏好可以猜，禁忌不能猜错。分三类，分开记，因为违反后的后果不同。

| 类型 | 例子 | 违反后果 | 记录位置 |
| --- | --- | --- | --- |
| 硬约束 | 首屏 LCP ≤ 2.5s；必须全键盘可达；不支持自动播放 | 功能不可用/验收失败 | 项目 DESIGN.md + profile（domain=流程/合规） |
| 品牌红线 | 禁用紫色渐变；标题必须用自有字体；Logo 周围留白 ≥ 1x | 品牌失真、返工 | 品牌规范 + profile（domain=色彩/字体排印） |
| 合规红线 | 同意默认不勾选；价格含税口径；AI 生成内容要标识 | 法律风险、下架 | 法务口径 + profile（domain=合规） |

可直接复制的空模板：

```markdown
## 禁忌
### 硬约束（违反 = 不可交付）
- [ ] 
### 品牌红线（违反 = 返工）
- [ ] 
### 合规红线（违反 = 法律/平台风险）
- [ ] 
```

采集问句（一次问一类，别混着问）：

1. 「这个项目有什么是绝对不能出现的？」（品牌）
2. 「上线前必须过哪些检查？谁签字？」（硬约束）
3. 「哪些话不能写、哪些数据不能收、哪些地区不能默认？」（合规）

禁忌要带来源与日期：`禁用紫色渐变（2026-10 品牌手册 v3，市场部确认）`。没有来源的禁忌，下个季度就会被当成个人偏好删掉。

## §4 审美基线采集

### 4.1 用 5 张图，不用 5 个形容词

准备 5 张**同品类、不同气质**的参考图，编号 A–E。不要拿 5 张都很像的图——那测不出偏好，只测得出品类。

选图维度（每张只主打一个）：

- A 极简：大留白、少颜色、字重克制；
- B 编辑：强网格、衬线标题、信息密度高；
- C 技术：等宽字体、tabular-nums、深色底；
- D 温暖：圆角、暖色、插画/摄影;
- E 大胆：高饱和、大字号、非常规构图。

### 4.2 追问三句

1. 「哪张最接近你想要的方向？为什么？」——理由比选择重要。
2. 「哪张最不像？哪一点让你排斥？」——负参照往往更稳定。
3. 「如果只能从选中的那张保留一个细节（颜色/字体/间距/图形），你留哪个？」——拿到优先级。

### 4.3 记录格式

```markdown
- 选择：B（编辑感）
- 理由：\"看起来像一本认真做的行业报告，不像 SaaS 广告\"
- 排斥：E（\"太吵，像促销页\"）
- 保留细节：标题的衬线 + 12 栏网格
- 推断 token：标题衬线 / 正文无衬线 / 8pt 基线 / 主色低饱和
```

推断出的 token 要标「推断」，等第二次独立证据再晋升（见 §7）。不要在一次对话后就写「用户喜欢编辑风」。

### 4.4 不要做的事

- 不要让用户填「简约 / 高级 / 科技感」——这三个词在 10 个人嘴里是 10 个意思；
- 不要用 Dribbble 热门图当唯一参照——它们衡量的是设计师的点赞，不是用户的场景；
- 不要把「客户老板喜欢的图」当成「用户基线」——先确认拍板人和使用者是不是同一个人。

## §5 画像 → 设计决策映射表

这张表是画像的出口：左边是信号，右边是能直接执行的动作。表里没有对应动作的信号，不配进画像。

| # | 画像信号 | 设计动作 | 常见反例 |
| --- | --- | --- | --- |
| 1 | 怕总价被加料 | 总价前置、税费/服务费逐项、结账不再新增费用 | 到支付页才显示服务费 |
| 2 | 怕重复填表 | 单页完成、自动填充、进度可保存 | 五步向导，每步都重新登录 |
| 3 | 怕误操作不可逆 | 危险操作二次确认 + 撤销窗口 | 删除即永久，无回收站 |
| 4 | 从竞品迁移，已试过并失败 | 首屏直接给差异点，不做品类科普 | 首屏还在讲「什么是 OKR」 |
| 5 | 时间压力大（值班/急诊/客服） | 大点击区、键盘优先、合理默认值 | 每个字段都必填、无默认 |
| 6 | 审美基线偏编辑感 | 衬线标题 + 12 栏网格 + 高信息密度 | 套通用 SaaS 模板再换主色 |
| 7 | 品牌禁用某色/某字体 | 在 token 层锁死，组件不暴露该值 | 只在文档里写「尽量别用」 |
| 8 | 合规要求明示同意 | 默认不勾选、拒绝与同意同样显著 | 预勾选 + 灰色小字 |
| 9 | 移动端单手操作 | 主操作落在拇指区，次要操作上移 | 底部堆 5 个同等权重的按钮 |
| 10 | 多语言/长文案 | 文案预留 30% 长度、不用文字做图标 | 中文文案写死进按钮 |
| 11 | 读屏/键盘用户 | 语义结构、焦点顺序、可见焦点环 | div 堆出来的「按钮」 |
| 12 | 数据敏感/内部合规 | 本地处理优先、上传前明示范围 | 默认全量上传，不说明用途 |
| 13 | 怕被审计追责 | 留痕、版本、可导出的凭证链 | 只存最终状态，无操作记录 |
| 14 | 多人协作、角色不同 | 权限分层、只读视图、变更通知 | 所有人一个编辑权限 |

用法：任务开始时，从 `memory/profile.md` 的 active 规则里取与本任务同域的条目，逐条对照本表找动作；找不到动作的规则，要么补动作，要么降级。

## §6 反模式

1. **把 average user 当画像**：为了「大多数人都能用」而砍掉边界，最后谁都不顺手。切片法就是解药。
2. **用年龄性别代替场景**：「年轻人喜欢短视频」解释不了为什么他在填报销单时恨透了动效。
3. **画像写完不更新（僵尸画像）**：上线三个月，用户结构早变了，画像还停在立项会。证据变了就改，改不动就标 weakened。
4. **只写喜欢，不写怕**：喜欢决定风格，怕决定结构；只写喜欢的画像做不出防错。
5. **把一次反馈当画像**：一个人一次抱怨是线索，不是规则。≥2 条独立证据才能晋升（§7）。
6. **用画像当挡箭牌**：「用户不会用」经常是设计没做好；先把任务测试跑一遍再怪用户。
7. **画像写成小说**：三页人物小传，没有一个字能落到控件上。判据回到 §0：能改变哪个设计动作？
8. **把拍板人当用户**：买单的人、使用的人、被报表影响的人，可能是三个切片，不能互相代替。

## §7 与 memory/profile.md 的接线

### 7.1 三层结构

```text
会话（当次任务）  →  memory/journal.jsonl（只追加，原始信号）
                  →  memory/profile.md（可重写，晋升后的规则）
                  →  本文件（怎么采集、怎么用）
```

- journal 记「发生了什么」：date / task / carrier / user_quote / signal_type / decision / outcome / closed_at / evidence_ref。
- profile 记「因此确定什么」：rule / domain / first_seen / confirmations / evidence_refs / status。
- 本文件不存具体用户数据，只存方法。

### 7.2 采集：任务收尾就记

```bash
python scripts/memory.py add --task "定价页改版" --signal correction \
  --quote "总价要放最上面" --decision "总价先行"
```

- 有原话才用 `explicit_preference` / `correction`，没有就 `none`，任务收尾指令用 `process`；
- 不替用户总结「他应该喜欢 X」——journal 里只放他说过/做过的；
- `outcome` 默认「待观察」，闭环时回填 `closed_at`。

### 7.3 晋升：≥2 条证据 + 用户确认

```bash
python scripts/memory.py promote     # 输出候选，不写文件
python scripts/memory.py apply --rule "总价先行" --domain 合规 --evidence 12,31
python scripts/memory.py validate
```

- `promote` 只认 `explicit_preference` / `correction`，同域且决策措辞等价（相似度 ≥ 0.7）才聚类；
- `apply` 要交互输入 `y` 才写入，写入后 `confirmations` 自动等于证据数；
- `validate` 会检查 profile 里每条 `evidence_refs` 都能在 journal 找到，且不是 `none` / `process`。

### 7.4 使用：任务开始时读什么

1. 读 `profile.md` 的 active 规则，同域优先，作为硬约束；
2. 读 `journal.jsonl` 最近 5 条同域记录，看有没有「上次踩过的坑」；
3. 两条都没有，就按 §1 五问现场采集，不要凭印象补。

### 7.5 边界

- 会话里的推测不进文件；文件里每一条都要能指回证据；
- 用户否定过的规则标 `retired`，保留一行原因，不静默删除；
- 每季度重写一次 profile，把 active 压到 20 条以内；
- 画像与证据冲突时，以 journal 为准。
