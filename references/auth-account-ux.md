# 认证与账户体验（Authentication & Account UX）

> 登录、注册、Passkeys / WebAuthn、MFA、验证码、账户恢复、会话与登出。
> 本资产的第一原则：**认证不是一道门，是一条可失败、可恢复、可退出的路径。**
> 取源日期 2026-11-14。所有数值标了出处；没有出处的写「工程约定」，不冒充规范。

---

## §0 立场与三条裁决

**立场**：认证界面的目标不是「把人挡住」，而是「让本人进来得足够快，让冒充者进来得足够难，并且两条路都不能把人锁死」。凡是只优化前者的设计，最后都在客服工单里偿还。

### 裁决一：先判「这一步是证明身份，还是建立身份」

WCAG 2.2 SC 3.3.8 的原文范围写死了：

> "This success criterion is focused on authentication of existing users. It does not cover creation of a username or initiation of an account."

这句话把认证体验切成两半：

| 阶段 | 规范覆盖 | 设计重点 |
|---|---|---|
| 登录 / 二次验证 / 重认证 / 恢复 | SC 3.3.8 AA + 3.3.9 AAA | 不得要求认知功能测试；必须有密码管理器/粘贴/生物识别等机制 |
| 注册 / 建账号 | **不被 3.3.8 覆盖**（3.3.9 同样不覆盖） | 靠「少字段、规则常驻、强度计、不重复字段」降低放弃率 |

把注册页的问题当成 3.3.8 问题去引条文，是这一行最常见的引用错误；反过来，注册页也不因此获得「可以随便加认知测试」的豁免——OWASP 与 NIST 的可用性条款照样管。

### 裁决二：密码的现行共识已经整体反转，旧规则多半是伤害可用性且没有安全收益的仪式

NIST SP 800-63B-4（2025-08-26 发布，替代 63B-3）与 OWASP ASVS 5.0 同时把「复杂度、轮换、提示问题、邮箱当因素」判为负资产。**凡是「看起来更安全」的旧规则，先当作需要举证的嫌疑项**（详见 §4 反神话表）。

### 裁决三：Passkeys 是默认推荐路径，不是可选装饰；创建时机在「账号已验证之后」

web.dev 的注册指南把前置条件写得很直白：

> "The user account is verified through a secure method (for example, email, phone verification, or identity federation) within a meaningfully short window."
> "Warning: Avoid password-only verification. If the password is leaked, attackers could create a passkey and compromise the account."

所以「注册第一步就弹 Create a passkey」是错序：那时账号还没被证明属于这个人，攻击者拿泄露密码就能种一把永久钥匙。正确顺序是**先证明、后种钥匙**。

## §1 判层：六问决定你该改哪一层

按顺序问，任一问答完就停，不要六问全做。

| # | 问题 | 答「是」去哪 | 答「否」去哪 |
|---|---|---|---|
| Q1 | 这一步是**证明身份**（登录/二次验证/重认证/恢复）还是**建立身份**（注册）？ | 证明 → §2 §5 §6 §7 §8 §10 | 建立 → §3 §4 |
| Q2 | 失败时用户还有**第二条路**吗（忘记密码 / 恢复码 / 换设备 / 客服）？ | 有 → 只改界面层 | 没有 → 先补恢复路径（§8），否则其余优化都是给死路刷漆 |
| Q3 | 这个账号的 **AAL 目标**是多少（AAL1 / AAL2 / AAL3）？ | 影响会话时长与因素数量（§9 时间表） | 未定义 → 按「有资金/隐私风险 = AAL2」起步 |
| Q4 | 用户此刻在**什么设备、什么场景**（手机单手 / 公共电脑 / 无障碍需求）？ | 移动端输入成本翻倍（§3.1） | 桌面 → 可保留较长的会话 |
| Q5 | 这是**首次**还是**回归**（登录 / 重认证 / 换设备）？ | 换设备 → 跨设备 passkey（§5.6） | 回归 → 会话与记忆成本优化 |
| Q6 | 后面有没有**不能失败的商业动作**（结账 / 提交订单）？ | 有 → 游客通道优先（§3.2） | 无 → 可要求账号 |

### §1.1 十二场景判层表

| 场景 | 判层 | 第一条动作 | 禁止 |
|---|---|---|---|
| 电商首次购买前要求注册 | 建立身份 + 商业动作 | 先给游客结账，成交后再邀请建账号 | 加购前弹注册墙 |
| B 端后台登录 | 证明身份（AAL2） | 企业 SSO 优先，本地密码作为兜底 | 强制每 90 天改密 |

| 内容站评论前登录 | 证明身份（AAL1） | 第三方登录 + 邮箱 magic link | 要求建密码才能评论 |

| 企业 SSO 回调失败 | 证明身份 | 明确错误 + 回退本地登录入口 | 白屏 / 无限跳转 |
| 账号注销 | 账户生命周期 | 二次确认 + 冷静期 + 可撤回 | 注销入口藏在三层设置里 |
| 未成年人模式 | 账户生命周期 | 监护人验证 + 最小化收集 | 用生日自证 |

## §2 登录界面解剖（证明身份层）

### §2.1 最小字段集与标记

登录界面只该有两件事：**一个标识符**、**一个秘密**。每多一道必填就多一次放弃机会。

| 元素 | 正确写法 | 理由 |
|---|---|---|
| 标识符（只收邮箱） | `<input type="email" autocomplete="username" ...>` | `username` token 让密码管理器知道这是账号名 |
| 标识符（用户名或邮箱） | `<input type="text" autocomplete="username" ...>` | 用 `type="email"` 会强制邮箱键盘并拦截合法用户名 |
| 密码 | `<input type="password" autocomplete="current-password" ...>` | 见 §2.2 token 表 |
| 提交 | `<button type="submit">` | 不要用 `div` 绑 click；Enter 必须能提交 |
| 忘记密码 | 链接紧贴密码框下方 | NN/g 登录三件套之一 |

必须同时给：`autocapitalize="none"`、`autocorrect="off"`、`spellcheck="false"`。中文输入法在密码框里被自动上屏是真实事故，`autocapitalize` 在 iOS 上还会把首字母变大写导致登录失败。

### §2.2 `autocomplete` token 表（MDN 逐字）

| token | MDN 原文 | 用在哪 |
|---|---|---|
| `username` | "A username or account name." | 登录名 / 账号名 |
| `current-password` | "The user's current password." | 登录、重认证、改密时输旧密码 |
| `new-password` | "A new password. When creating a new account or changing passwords, this should be used for an \"Enter your new password\" or \"Confirm new password\" field..." | 注册 / 改密；**确认密码框也用它** |
| `one-time-code` | "A one-time password (OTP) for verifying user identity that is used as an additional factor in a sign-in flow." | 短信 / 邮件 / TOTP 验证码 |
| `webauthn` | "Passkeys generated by the Web Authentication API, as requested by a conditional navigator.credentials.get() call..." | 条件式 passkey 自动填充，**必须是 token 列表最后一项** |
| `email` | "An email address." | 只收邮箱的字段（注册页） |
| `tel` / `tel-national` | "A full telephone number, including the country code." / 去掉国家码 | 手机号，按是否带国家码选 |
| `postal-code` / `cc-number` | 邮编 / 卡号 | 结账（详见 `pricing-checkout.md`） |

三条硬纪律：

1. **`autocomplete="off"` 不是安全措施**。MDN 原文："In most modern browsers, setting autocomplete to \"off\" will not prevent a password manager from asking the user if they would like to save username and password information, or from automatically filling in those values in a site's login form." 它只会让浏览器不再帮你填，用户更可能用弱密码。
2. **编造 token 同时违反 WCAG**。MDN："also fails the WCAG requirement above, since the input purpose is no longer programmatically determinable."（对应 SC 1.3.5 Identify Input Purpose, AA）
3. **确认密码框写 `new-password` 而不是 `current-password`**，否则密码管理器会把旧密码填进「确认新密码」，用户看到两个框都满就提交，服务端比较失败，然后用户以为系统坏了。

### §2.3 显示密码：默认遮挡 + 显式切换

NN/g 有一处代际差，必须原文对照着读：

- 2009《Stop Password Masking》："Usability suffers when users type in passwords and the only feedback they get is a row of bullets."；"Users make more errors when they can't see what they're typing"。
- 2015《Password Creation》：桌面默认遮挡 + "Show password" 复选框；移动端默认明文 + "Hide password"。
- 2017《Checklist》：登录页默认遮挡 + 显式 Show password。

**现行裁决**：桌面与移动统一「默认遮挡 + 显式切换」，理由是 2017 之后用户对明文密码的旁观顾虑上升，而切换成本只有一次点击。切换控件必须是可聚焦的 `button`，带 `aria-pressed`，文案在「显示密码 / 隐藏密码」之间切换，不能只靠 hover 出现的眼睛图标。

### §2.4 粘贴、密码管理器与键盘

| 规则 | 做法 | 依据 |
|---|---|---|
| 允许粘贴 | 不禁 `paste`，不禁右键 | WCAG F109；"Blocking people from pasting into authentication fields ... would force the user to transcribe information and therefore fail this criterion" |
| 允许密码管理器 | 标准 `<form>` + 标准 `name`/`autocomplete`，不要 `readonly` 直到聚焦 | 同上 |
| 允许单 Tab 切换 | 用户名 → 密码 → 提交 | OWASP："Allow users to navigate between the username and password field with a single press of the Tab key." |
| 不要 JS 清空已填充值 | 不要 `onload` 清空、不要 `value=""` 覆盖 | 会毁掉密码管理器填充 |
| Caps Lock 提示 | 可做，但只作提示，不阻断 | 工程约定（无规范数值） |

### §2.5 错误提示：泛化是安全要求，不是冷漠

OWASP Authentication Cheat Sheet 原文：

> "An application should respond (both HTTP and HTML) in a generic manner."

正确示例："Login failed; Invalid user ID or password."
错误示例："Login failed; account disabled." / "Login failed; this user is not active."

落地四条：

1. **一句话覆盖四种失败**（不存在 / 密码错 / 被锁 / 未激活），措辞统一为「用户名或密码不正确」。
2. **字段级错误用 `aria-describedby` 关联**，并在提交后把焦点移到错误摘要或第一个错误字段（`accessibility.md` §焦点）。
3. **不要清空输入**。密码错时保留用户名，密码框可清空但要让用户能再贴一次。
4. **时序不要泄露**。OWASP："the business logic itself can bring a discrepancy factor related to the processing time taken"——存在与不存在的账号走同一代码路径与同一状态码。

### §2.6 提交态与防重复

- 提交后按钮进入 `disabled` + 文案变「正在登录…」，但**不要**把整个表单 `pointer-events:none`（读屏用户会失去焦点）。
- 网络错误与服务端拒绝必须区分：前者「网络异常，请重试」，后者「用户名或密码不正确」。
- 连续失败后**才**升 CAPTCHA（OWASP："It may be more user-friendly to only require a CAPTCHA be solved after a small number of failed login attempts"）。CAPTCHA 一旦出现，必须同时满足 §10 的认知测试规则。

## §3 注册与账号创建（建立身份层）

### §3.1 输入成本是设计的起点

NN/g 转述 NordiCHI 2014 的研究："entering a password character on mobile takes almost twice as much time than on the desktop, and as a result people tend to create weaker passwords on mobile."（样本量原页未给，引用时只写结论，不写样本数。）

推论：移动端**每一个字符**都要有理由。注册页的字段数是最贵的指标。

### §3.2 游客优先，账号后置

Baymard 的弃购原因分布（美国网购用户、自报、多选、剔除「只是逛逛」）里：

> "18% The site wanted me to create an account"

NN/g："Forcing registration causes lost sales."；"It is common for sites that add guest checkout to immediately realize increased sales."

落地：结账前提供「以游客身份继续」，成交后用一个「保存这次订单」的动作邀请建账号。不要用「注册才能看运费」这种半步强制。

### §3.3 密码规则：常驻可见 + 实时强度

NN/g："State the password requirements, and make sure that the user can see them the entire time that the field is selected."；"most people won't notice it or won't bother expanding that link"（折叠说明无效）。

强度计用 zxcvbn-ts 一类**基于猜测次数**的算法，不要用「有大写 +1 分」的自造规则；强度计只做建议，不做硬拦截（拦截会逼用户加 `!` 然后忘记）。

### §3.4 不要重复字段

NN/g："Do not repeat fields (e.g., two password fields, two email fields). Typing passwords is painful enough; typing them twice is twice as painful."

若合规/审计强制保留确认密码：两个框都写 `autocomplete="new-password"`，并在用户 paste 到第一个框时自动填充第二个（值相同，风险为零）。

### §3.5 邮箱验证：链接可以，阻断不行

NN/g 2017 建议"不要用邮件确认注册"，改短信码（"If you must confirm credentials, do so by sending users a code in a text message instead of a link through email."），理由是邮件链接要切应用。

但「邮箱即账号」的产品无法取消邮箱验证。裁决：

- **允许**先完成注册并进入产品，把「验证邮箱」降级为横幅提醒 + 敏感操作前置（发信、支付、改密）。
- **不要**把「点邮件链接」做成登录前置，否则每一次注册都在赌邮件送达率。
- 验证链接：一次性、短有效期（工程约定 15–60 分钟）、点击后落地页要说清「已验证」并能继续原来的动作。

### §3.6 不暴露账号是否存在

注册成功提示按 OWASP 模板："A link to activate your account has been emailed to the address provided."
反例："This user ID is already in use."

代价是用户可能重复注册同一个邮箱却收不到信；补偿手段是提示里加一句「若该邮箱已注册，你会收到一封登录/重置邮件」，把两条路都留出来。

### §3.7 第三方登录与账号合并

- 社交按钮与邮箱登录**同尺寸、同视觉权重**（Google 原文："should be displayed at least as prominently as other third party sign-in options"）。
- 同一邮箱用密码注册过、又用 Google 登录：**不要**静默建两个账号，也不要自动合并；让用户在原账号上「绑定 Google」，并给一次确认。
- 第三方登录失败的错误必须可读（「Google 登录未完成」而不是 `invalid_request`）。

## §4 密码策略反神话表（把「听起来安全」逐条对到原文）

| 民间说法 | 现行规范 | 依据 |
|---|---|---|
| 「最少 8 位」 | **单因素密码 SHALL ≥15 字符**；仅作为 MFA 的一环时 MAY 更短但 SHALL ≥8 | NIST 800-63B-4 §3.1.1.2#1 |
| 「必须大小写+数字+符号」 | **SHALL NOT** 强加组合规则 | 同上 #5 |
| 「90 天强制改密」 | **SHALL NOT** 要求周期性改密；仅在有妥协证据时 SHALL 强制改 | 同上 #6 |
| 「最长 16/20 位」 | **SHOULD 至少允许 64**——这是下限不是上限 | 同上 #2 |
| 「密码不能有空格/中文」 | 必须接受 Unicode 与空格，按码点计长度 | 同上 #4 |
| 「超长就截断」 | **SHALL** 校验完整输入，不截断（trim 首尾空格只是 MAY 且有条件） | 同上 #9 |
| 「黑名单查子串」 | **SHALL** 比对整串，且 SHALL 说明拒绝原因 | 同上 |
| 「密码提示问题」 | 禁用知识型认证（KBA）；ASVS 6.4.2 "Do not use security questions for authentication or re-authentication" | ASVS 5.0 V6 |
| 「邮箱可以做二次因素」 | **SHALL NOT** 用邮件做带外认证 | NIST §3.2.x |
| 「短信验证码被全面禁止」 | SMS/PSTN 是**唯一的 RESTRICTED 认证器**，不是禁止；需满足 CSP 的四项 SHALL | NIST §3.2.9 |
| 「密码要有 60 bits 熵」 | 现行文本不再用「熵」做门槛，改看长度与黑名单 | 反陈旧裁决 |
| 「OTP 必须 30 秒」 | 30 秒是 TOTP 实现参数，不是 NIST 取值 | 反陈旧裁决 |
| 「锁定要按 IP 计数」 | 计数应绑**账号**（OWASP："should be associated with the account itself, rather than the source IP address"） | OWASP |

**强度口径**（OWASP，比 NIST 更宽松，写清来源即可）：有 MFA 时 <8 字符算弱；无 MFA 时 <15 字符算弱；最大长度至少 64 以容纳 passphrase；无组合规则；避免周期改密。
**ASVS 5.0 的已知错位**：正文仍引用 800-63-3，且 6.2.1 的 ≥8（建议 15）与 NIST 的 ≥15 不一致——**引用时必须分标来源，不要合成一个数**。

### §4.1 限速与锁定

- NIST：单个账户对单个认证器的**连续失败上限 100 次**后禁用（这是上限，可更严）。
- OWASP 的三参数：阈值、观察窗口、锁定时长；指数退避从 1 秒起翻倍；"Amount of time to delay after each account lockout (max 2-3, after that permanent account lockout)."
- 界面义务：告诉用户「还可以试几次」「请等多久」，不要只给一个转圈。
- 反模式：失败三次就把账号锁死且不给自助解锁——这不是安全，是把用户推给客服。

## §5 Passkeys / WebAuthn（首选路径）

### §5.1 它解决的是什么

passkey 是**存在认证器里的密钥对**：私钥不出设备，公钥存服务端；登录时服务端发随机 challenge，设备用私钥签名。三个直接后果：

1. **没有共享秘密可被拖库**——服务端只有公钥。
2. **钓鱼失效**——签名绑定 rp.id（域名），假站拿到 challenge 也签不出有效断言。
3. **跨设备同步**——iCloud Keychain / Google Password Manager 负责同步，站点不承担。

### §5.2 参数表（W3C WebAuthn L3 实测）

| 参数 | 规范值 | 设计含义 |
|---|---|---|
| `challenge` | "At least 16 bytes that include at least 100 bits of entropy"（§5.1.3） | 服务端生成，**每次新随机** |
| `rp.id` | 必须等于或为 origin 有效域的**可注册域后缀**；否则 `SecurityError`（§5.1.3） | 不能填公网后缀（如 `co.uk`）；`localhost` 例外 |
| `user.id` | 1–64 字节，opaque（"is not meant to be displayed to the user"） | **不放邮箱/用户名**；账号创建时生成后永不变 |
| `user.name` / `displayName` | 账号名 / 显示名 | 会在系统账号选择器里显示，别放敏感信息 |
| `residentKey` | 缺省时：`requireResidentKey` 为 true 则 required，否则 **discouraged** | 要「无用户名登录」的 passkey，必须显式 `residentKey: "required"` |
| `requireResidentKey` | 默认 `false`，仅为 L1 兼容保留 | 与 `residentKey` 同时给时要一致 |
| `userVerification` | 默认 `"preferred"` | 平台认证器本来就要屏锁；写 `required` 会让无 UV 能力的设备直接失败 |
| `attestation` | 默认 `"none"` | 不要为了「更安全」要 attestation：打断流程、暴露设备信息、还得维护证书链 |
| `timeout` | 推荐范围 300000–600000 ms，推荐默认 **300000 ms（5 分钟）**（§15.1） | 这是提示不是硬上限；客户端可依 WCAG 2.2 调整 |

`pubKeyCredParams` 至少给 `-7`（ES256）与 `-257`（RS256），顺序按服务端偏好。

### §5.3 能力检测：三层，不要靠 UA 字符串

```js
// 1) API 存在
if (!window.PublicKeyCredential) return hidePasskeyUI();

// 2) 客户端能力（新）：conditionalGet 与 passkeyPlatformAuthenticator
const caps = await PublicKeyCredential.getClientCapabilities?.();
const canPasskey = caps?.conditionalGet === true && caps?.passkeyPlatformAuthenticator === true;

// 3) 旧接口兜底（仍在用，但已被能力接口取代）
const hasPlatformUV = await PublicKeyCredential
  .isUserVerifyingPlatformAuthenticatorAvailable?.() ?? false;
```

`getClientCapabilities()` 返回的枚举里与本主题相关的有：`conditionalCreate`、`conditionalGet`、`hybridTransport`、`passkeyPlatformAuthenticator`、`signalAllAcceptedCredentials`、`signalUnknownCredential`（§5.8.7）。**能力为 false 时不要渲染按钮**，渲染了再失败比不渲染更伤信任。

### §5.4 创建时机：四个，且都要「账号已验证」

web.dev 列出的四个时机：

1. 注册过程中或注册后；
2. 登录后；
3. 用另一台设备的 passkey 登录后（cross-platform）；
4. 专门的 passkey 管理页。

共同前置（同页原文）：账号在「meaningfully short window」内通过安全方式验证过（邮箱、手机号、身份联合），且**避免只靠密码验证**。

界面纪律：

- 一次只问一次，跳过要有明确出口（"稍后" 不是 "取消" 的同义词，文案要写「以后再说」）。
- 解释收益用一句话，不用技术词：「下次用指纹或面容直接登录，不用记密码」。
- 创建成功后**立刻告知**（web.dev 建议发通知/邮件），因为用户往往不知道刚刚发生了什么。

### §5.5 登录：条件式 UI（conditional mediation）

这是 passkey 体验的分水岭：**passkey 出现在用户名输入框的自动填充里**，而不是一个独立按钮。

```html
<input type="text" name="username" autocomplete="username webauthn" ...>
```

```js
const available = await PublicKeyCredential.isConditionalMediationAvailable?.();
if (available) {
  navigator.credentials.get({
    mediation: "conditional",
    publicKey: { challenge, rpId, allowCredentials: [], userVerification: "preferred" },
  }).then(onSuccess).catch(onError);
}
```

四条规范性事实（L3 §5.1.4）：

- `autocomplete` 里的 `webauthn` 必须紧跟在最后一个 Normal/Contact token 之后，例如 `"username webauthn"`、`"current-password webauthn"`。
- 条件式请求**只对可发现凭证（discoverable credentials）生效**：原文 "This prevents non-discoverable credentials from being used during conditional requests."
- 条件式下**不得弹模态 UI**，除非用户此前已同意创建凭证；发现凭证后再让用户选。
- 条件式下客户端会把 `requireUserPresence` 与 `requireUserVerification` 都设为 FALSE，是否验证由后续流程决定。

### §5.6 跨设备（hybrid）：交给浏览器，不要自己画二维码

`hybridTransport` 能力存在时，桌面端发起登录，浏览器会给出「用另一台设备」的二维码/邻近流程。站点只需要：文案写「用手机扫描」，以及在用户选了「另一台设备」后**不要中途跳页**（跳页会中断 ceremony）。

### §5.7 错误映射：哪些该说、哪些该吞

| 错误名 | 含义 | UI 处理 |
|---|---|---|
| `NotAllowedError` | 用户取消、超时、或没有可用认证器 | **静默回退**到密码/其他方式；不要弹「认证失败」 |
| `InvalidStateError` | 该设备已有此账号的 passkey（重复注册） | 视为成功：提示「此设备已可直接登录」 |
| `SecurityError` | `rp.id` 不匹配、非安全上下文 | 工程 bug：记日志、给兜底，不要向用户解释域名 |
| `AbortError` | 代码主动 `abort()`（如用户切走） | 静默 |
| `NotSupportedError` | 算法/参数不被支持 | 记日志 + 回退其他方式 |
| `UnknownError` | 其他 | 通用失败文案 + 重试 |

web.dev 对 `InvalidStateError` 的原话值得抄进评审意见："A passkey already exists on the device. No error dialog will be shown to the user. The site shouldn't treat this as an error. The user wanted the local device registered and it is."

### §5.8 凭证管理页

- 列出每一把 passkey：设备名 / 创建时间 / 最后使用（若可测）。
- 支持改名与删除；**最后一把不能删**，除非已存在另一因素（否则用户把自己锁在门外）。
- 删除后调用 `signalUnknownCredential()`（单把）或 `signalAllAcceptedCredentials()`（全量同步），让浏览器清理失效凭证——否则用户会反复点到一个必失败的 passkey。
- 名称由用户给（「我的 MacBook」），不要用 AAGUID 猜出来的营销名当唯一标识。

## §6 第二因素的选择与编排

### §6.1 因素强度排序（同强度下按体验排）

`passkey` ≈ 硬件密钥 > 平台生物识别 > TOTP > 推送确认 > 短信 OTP > 邮件（**不可用作因素**）。

OWASP 引用的 Microsoft 分析："suggesting that it would have stopped 99.9% of account compromises"——这句话适合写在内部立项文档里，不适合写在用户界面上。

### §6.2 步骤数与节奏

- 两个因素足够；三步以上必须有强理由（如 AAL3 的硬件 + 生物识别）。
- 首次登录新设备才要求第二因素；已信任设备给「记住此设备 30 天」——**30 天是工程约定，不是规范值**，写清。
- 敏感操作（改密、改邮箱、提现、删除账号）走**重认证**，不要重走完整登录。

### §6.3 TOTP

- 6 位数字，30 秒窗口，服务端容忍前后各 1 个窗口（时钟偏差）。
- 显示剩余秒数会让用户焦虑，不必须；但重试要有「等到下一组」的提示。
- 绑定流程必须给「手动输入密钥」与「复制密钥」，不能只给二维码（桌面端扫码依赖手机）。

### §6.4 推送确认与 MFA 疲劳

- 推送确认必须带**数字匹配**（登录页显示两位数字，用户在手机上选同样的数字）或上下文（地点/设备）。只有「批准/拒绝」两个按钮的推送，已经是公开的钓鱼手法。
- 限制推送速率：一分钟最多 1–2 次，超过直接降级为输码。
- 用户拒绝后，界面要给「这不是我」的后续动作（改密 + 踢出所有会话）。

### §6.5 恢复码

- 熵 ≥64 bits（NIST §4.2.1.1），一次性，用后作废并提示重新生成。
- 展示必须一次给全，并给「复制 / 下载 / 打印」；**不要**只显示一次却不给下载。
- 保存位置提示用用户能懂的话（「存到密码管理器里」），不要写「妥善保管」。

### §6.6 绑定多个因素时的顺序

先绑强因素，再绑弱因素；每一步都要能「跳过并稍后」。不要把「绑定手机号」写成不可跳过的强制项，除非业务确实需要（如金融 KYC）。

## §7 一次性口令的单框

### §7.1 单框，不是六个框

六个独立输入框在粘贴、读屏、退格、自动填充上全部是坑：用户粘贴 6 位会只进第一格；读屏会把 6 个框读成 6 个字段；`autocomplete="one-time-code"` 在 iOS 上只对单框可靠。

```html
<label for="otp">验证码</label>
<input id="otp" name="otp" type="text" inputmode="numeric" pattern="[0-9]*"
       maxlength="6" autocomplete="one-time-code" aria-describedby="otp-hint">
<p id="otp-hint">6 位数字，已发送至 138****8000</p>
```

视觉上可以用 `letter-spacing` 做出等宽分隔感，但 DOM 里只有一个 input。

### §7.2 行为

| 行为 | 做法 | 理由 |
|---|---|---|
| 粘贴 | 允许整段粘贴，自动取前 6 位数字 | 手抄即 transcription，触发 SC 3.3.8 |
| 自动提交 | 满 6 位可自动提交 | 少一次点击；失败必须能改 |
| 自动前进 | **不要**用 6 框自动跳格 | 抢焦点会打断读屏与修正 |
| 重发 | 倒计时（工程约定 30–60 s），到期可重发 | 防止用户狂点 |
| 过期 | 短信/语音码 10 分钟（NIST 下发码口径）；邮件码 24 小时 | 到期文案要说明「重新获取」 |
| 错误 | 明确剩余次数与等待时间 | NIST §8 可用性 |

### §7.3 无障碍红线

- 不要要求「输入第 1、3、5 位」——WCAG 明确把按位输入列为失败。
- `inputmode="numeric"` 给数字键盘；不要 `type="number"`（会出上下箭头与科学计数法）。
- 错误用 `aria-describedby` 关联，不要只变红。

## §8 账户恢复

### §8.1 忘记密码

- 入口固定在登录表单密码框下方，文案「忘记密码？」。
- 流程：输邮箱 → 统一提示「如果该邮箱在我们的记录中，你会收到一封重置邮件」→ 邮件链接（一次性、短有效期）→ 设置新密码（`autocomplete="new-password"`，不重复字段）。
- OWASP 原话就是文案模板："If that email address is in our database, we will send you an email to reset your password."
- 重置链接点击后：立即失效、绑定当前会话、改完通知用户「密码已修改，若非本人请立即联系」。

### §8.2 恢复不得绕过 MFA

ASVS 6.4.3 的要求：重置流程不得成为绕过 MFA 的后门。做法：重置成功后仍要求第二因素，或强制踢出全部会话并要求重新登录。

### §8.3 magic link

邮箱链接登录（G218）是最省认知的路径之一：一次性、短有效期、点击即登录。风险是邮件被转发/被扫；对策是「链接一次性 + 绑定设备指纹可选项 + 登录后提示最近登录」。

### §8.4 没有邮箱、没有旧手机

必须留一条人工兜底：客服身份核验（订单号、注册时间、支付凭证），并给**延迟生效**（如 24 小时后才能改绑），防止社工即时接管。这条路径的界面要写清「需要多久」，不要让用户以为提交就生效。

### §8.5 恢复后的清理动作

改密/恢复成功后必须：撤销所有其他会话、通知用户、展示「最近登录设备」并要求确认。这三件事比「密码强度提示」更能降低二次损失。

## §9 会话、超时与登出

### §9.1 会话时长（NIST 800-63B-4）

| AAL | 总时长 | 空闲超时 |
|---|---|---|
| AAL1 | ≤30 天（SHOULD） | 未要求 |
| AAL2 | ≤24 小时（SHOULD） | ≤1 小时（SHOULD） |
| AAL3 | ≤12 小时（**SHALL**） | ≤15 分钟（SHOULD） |

界面义务（NIST §8 可用性）：**空闲超时前 2 分钟提示**；固定超时前提示保存草稿；给出「继续使用」的延长按钮。静默踢回登录页并丢失已填内容是常见事故。

### §9.2 「记住我」到底记什么

| 写法 | 实际含义 | 建议 |
|---|---|---|
| 勾选后延长会话 | 30 天免登录 | 可，但敏感操作仍要重认证 |
| 勾选后只记住用户名 | 下次预填账号 | 更安全，适合公共设备 |
| 不勾选也长期登录 | 会话永不失效 | 禁止 |

文案要写后果（「在这台设备上保持登录 30 天」），不要只写「记住我」。

### §9.3 多设备与全局登出

- 设置页给「登录设备」列表：设备名、地点、最后活跃、当前设备标记。
- 「退出所有设备」必须真的让服务端 token 失效，而不只是清本地 cookie。
- 改密/找回后自动执行一次全局登出，并在下次登录时告知。

### §9.4 前端会话状态

- 过期时间以服务端为准，前端不要自己算「还剩多久」然后放行。
- 多标签页同步：`storage` 事件 + `BroadcastChannel`，避免一个标签登出、另一个还在提交。
- 401 处理：不要无限重试；一次刷新失败即跳登录并带回跳地址。

## §10 无障碍与合规（这一节决定「能不能用」）

### §10.1 SC 3.3.8（AA）原文与四个例外

> "A cognitive function test (such as remembering a password or solving a puzzle) is not required for any step in an authentication process unless that step provides at least one of the following:"

| 例外 | 原文 |
|---|---|
| Alternative | "Another authentication method that does not rely on a cognitive function test." |
| Mechanism | "A mechanism is available to assist the user in completing the cognitive function test." |
| Object Recognition | "The cognitive function test is to recognize objects." |
| Personal Content | "The cognitive function test is to identify non-text content the user provided to the website." |

**cognitive function test** 的定义："A task that requires the user to remember, manipulate, or transcribe information." 关键在 **transcribe（转抄）也算**——所以「手抄短信验证码」落在测试范围内。而姓名、邮箱、电话「are not considered cognitive function tests as they are personal to the user and consistent across websites」。

**机制的来源可以是平台**："The mechanism may be explicitly provided in the content, or may be relied upon to be provided by either the platform or by user agents, including assistive technologies."——即浏览器自动填充、系统生物识别、密码管理器都算，你不必自己实现。

### §10.2 明确失败清单（评审直接打回）

| 做法 | 判定 |
|---|---|
| 禁止粘贴到密码/验证码框 | 失败（F109） |
| 阻止浏览器/密码管理器自动填充 | 失败，除非另有替代 |
| 要求输入密码的第 1、3、5 位 | 失败 |
| 必须手抄 2FA 验证码 | 失败（除非可粘贴/自动填充） |
| 拼写题、算术题、猜谜 | 失败 |
| 图形 CAPTCHA 只做「识别」 | 可以 |
| 图形 CAPTCHA 要求算「猫数 × 狗数」 | 失败（超出识别） |
| 音频 CAPTCHA 要求听写 | 失败 |
| 只在可疑时触发的 CAPTCHA | **同样受约束**："This criterion applies when these tests are used regardless of whether they are used every time or only triggered by specific scenarios." |

### §10.3 范围与多步

- 只覆盖已有用户认证，不覆盖建账号（§0 裁决一）。
- 多步认证「all steps need to comply」。
- 账户恢复也被覆盖："there needs to be a method that is not a cognitive function test."
- 显示密码是加分项不是要求："Providing a feature to optionally show a password can improve the chance of success..."

### §10.4 SC 3.3.9（AAA）差异

同一段要求，但只剩 Alternative 与 Mechanism 两个例外：不能再用「选图片」「选自己上传过的内容」过关。做政务/金融/医疗等可能被要求 AAA 的项目时，直接按 3.3.9 设计。

### §10.5 与 1.3.5 的联动

有效的 `autocomplete` token 同时满足 SC 1.3.5 Identify Input Purpose（AA）；编造 token 同时违反两者。这是「一次做对、两条过」的少数例子。

### §10.6 NIST §8 的可用性硬指标

| 项 | 值 |
|---|---|
| 最小字号 | 12 points |
| 允许尝试次数 | 至少 10 次 |
| 失败反馈 | 剩余次数 + 等待时长 |
| 空闲超时 | 前 2 分钟提示 |
| 固定超时 | 前提示保存 |
| 密码长度 | 允许 ≥64 字符 |
| 遮挡 | 易错场景必须可显示 |

### §10.7 读屏与焦点

- 错误摘要用 `role="alert"`（或 `role="status"` + 手动聚焦），**提交后把焦点移到摘要**，不要只播报。
- 每个错误用 `aria-describedby` 指回字段，字段加 `aria-invalid="true"`。
- 显示密码按钮用 `aria-pressed` 播报状态。
- 不要用 `aria-live` 播报「正在验证…」这类高频状态，会打断用户。

## §11 安全与体验的冲突裁决表

| 冲突 | 安全侧主张 | 体验侧主张 | 裁决 |
|---|---|---|---|
| 错误信息 | 明确指出哪里错，便于用户修正 | 泛化防枚举 | **泛化**，但给「忘记密码」与「联系支持」出口 |
| 锁定 | 失败多次直接锁 | 用户会被误锁 | **限速 + 退避**优先于锁定；锁定时给自助解锁 |
| CAPTCHA | 一进来就验证 | 增加认知负担 | **失败若干次后**才出现，且必须可粘贴/可替代 |
| 验证码 | 必须手输，防自动化 | 手抄违反 3.3.8 | **允许粘贴与自动填充**，防自动化靠服务端限速 |
| 会话 | 越短越安全 | 频繁重登很烦 | 按 AAL 定档（§9.1），到期前 2 分钟提示 |
| 社交登录 | 减少密码泄露面 | 账号合并复杂 | 提供但不替代；同邮箱冲突时让用户显式绑定 |
| 密码强度 | 强制复杂规则 | 用户会忘记 | **长度 + 黑名单 + 强度计**，不加强制规则 |
| 生物识别 | 不可撤销 | 最快 | 必须同时提供非生物替代（NIST §3.2.3） |

## §14 反模式 20 条

1. 注册第一步就弹「创建 passkey」。
2. 登录页 `autocomplete="off"`。
3. 确认密码框写 `current-password`。
4. 禁止粘贴密码或验证码。
5. 密码框 `oncopy/onpaste return false`。
6. 失败提示区分「账号不存在 / 密码错误 / 已锁定」。
7. 失败三次永久锁号且无自助解锁。
8. 要求 90 天改密。
9. 密码最多 16 位。
10. 用「输入第 1、3、5 位」做二次验证。
11. 6 个独立 OTP 输入框 + 自动跳格。
12. 手抄验证码是唯一方式，且不许粘贴。
13. 图形 CAPTCHA 出算术题。
14. 用户拒绝推送后仍反复弹。
15. 推送确认只有「批准/拒绝」。
16. 恢复流程绕过 MFA 直接改密。
17. 忘记密码提示「该邮箱未注册」。
18. 「记住我」默认勾选且不说明时长。
19. 改密后不撤销其他会话。
20. 把 passkey 说成「生物识别登录」（它是密钥，不是指纹）。

## §15 自检 20 条

1. 登录页是否只有 identifier + password 两个字段？
2. `autocomplete` 是否为 `username` / `current-password`（注册为 `new-password`）？
3. 是否允许粘贴、允许密码管理器？
4. 显示密码是否可聚焦、带 `aria-pressed`、文案切换？
5. 失败文案是否不区分原因？
6. 错误是否用 `aria-describedby` 关联并管理焦点？
7. 是否有「忘记密码」入口？
8. 注册是否去掉了重复字段（或两框都 `new-password`）？
9. 密码规则是否常驻可见？
10. 是否有强度计（基于猜测次数）？
11. 最大长度是否 ≥64？
12. 是否没有组合规则、没有周期改密？
13. 是否提供了 passkey 入口，且能力检测失败时不渲染？
14. 创建 passkey 是否在账号验证之后？
15. 是否实现了条件式 UI（`autocomplete="username webauthn"` + `mediation:"conditional"`）？
16. `NotAllowedError` 是否静默回退而不是弹错？
17. OTP 是否单框 + `one-time-code` + 允许粘贴？
18. 会话时长是否按 AAL 定档，到期前 2 分钟提示？
19. 改密/恢复后是否撤销其他会话？
20. 是否跑过「不许粘贴」与「读屏输验证码」两个场景？

### §16.2 条件式 passkey（JS）

```js
async function startConditionalPasskey() {
  if (!window.PublicKeyCredential?.isConditionalMediationAvailable) return;
  if (!(await PublicKeyCredential.isConditionalMediationAvailable())) return;

  const controller = new AbortController();
  try {
    const cred = await navigator.credentials.get({
      mediation: "conditional",
      signal: controller.signal,
      publicKey: {
        challenge: Uint8Array.from(atob(CHALLENGE_B64), c => c.charCodeAt(0)),
        rpId: location.hostname,
        allowCredentials: [],
        userVerification: "preferred",
        timeout: 300000,
      },
    });
    await fetch("/auth/passkey/verify", { method: "POST", body: JSON.stringify(serialize(cred)) });
    location.assign("/app");
  } catch (e) {
    if (e.name === "NotAllowedError" || e.name === "AbortError") return; // 静默
    console.warn("[passkey]", e.name);
  }
}
```

### §16.4 Python 静态校验器（实跑口径）

```python
# 检查一段登录/注册 HTML 是否踩了本资产列出的硬性反模式。
import re, sys

SAMPLE = """
<form>
  <input id="username" name="username" type="text" autocomplete="username">
  <input id="password" name="password" type="password" autocomplete="current-password">
  <button type="button" aria-pressed="false">显示密码</button>
  <input id="otp" name="otp" inputmode="numeric" autocomplete="one-time-code" maxlength="6">
</form>
"""

BAD_PATTERNS = [
    (r'autocomplete\s*=\s*["\']off["\']', "登录表单不许 autocomplete=off"),
    (r'onpaste\s*=\s*["\']return\s+false', "禁止粘贴违反 WCAG F109"),
    (r'type\s*=\s*["\']number["\']', "验证码不要用 type=number"),
]

def check(html: str):
    problems, oks = [], []
    for pat, msg in BAD_PATTERNS:
        if re.search(pat, html, re.I):
            problems.append(msg)

    if re.search(r'type\s*=\s*["\']password["\'][^>]*autocomplete\s*=\s*["\']current-password', html):
        oks.append("/ 密码框带 current-password")
    if re.search(r'autocomplete\s*=\s*["\'][^"\']*one-time-code', html):
        oks.append("/ 验证码带 one-time-code")
    if re.search(r'aria-pressed', html):
        oks.append("/ 显示密码切换带 aria-pressed")
    if re.search(r'<form[^>]*>', html):
        oks.append("/ 使用标准 form")

    return problems, oks

if __name__ == "__main__":
    problems, oks = check(SAMPLE)
    for line in oks:
        print("PASS", line)
    for p in problems:
        print("FAIL", p)
    print("总判定:", "PASS" if not problems else "FAIL")
    sys.exit(0 if not problems else 1)
```

## §17 取源限制

1. NIST 800-63B-4 的整页 `sp800-63b.html` 在抓取时截断于 §3.1.7，改按分页（authenticators / events / session / security / customer / passwords）取全，均 HTTP 200。
2. NIST 与 ASVS 存在**版本错位**：ASVS 5.0 正文仍引用 800-63-3；两者密码下限不同（8 vs 15），引用必须分标。
3. Apple HIG 的 HTML 页为 JS 渲染，只能取 JSON 端点 `developer.apple.com/tutorials/data/design/human-interface-guidelines/sign-in-with-apple.json`。
4. Google 品牌指南 `developers.google.com` 直连失败，改用 `developers.google.cn` 镜像（页面更新 2025-12-10）。
5. Google 当前版本**没有给按钮最小尺寸**，流传的「200px」无法在现行原文找到，本资产不采用。
6. Baymard 只取到 `cart-abandonment-rate` 的 18%；`checkout-flow-average-form-fields`、`guest-checkout` 为付费墙，数字未取到，不臆造。
7. NN/g `website-account-creation/` 返回 404（文章不存在）；`login-walls/` 抓取失败。
8. NN/g 2009 与 2015/2017 对「默认明文」结论相反，本资产按时间序标注代际差，取 2017 之后的做法。
9. W3C WebAuthn L3 用 `w3.org/TR/webauthn-3/` 全文离线核对（2.7 MB HTML → 597 KB 文本），关键段落逐行取证。
10. `simplewebauthn/simplewebauthn` 在 GitHub API 返回 404，真实仓库为 `MasterKale/SimpleWebAuthn`（2,393★ / MIT）。
11. 浏览器对 `getClientCapabilities()` 的支持始于 2025 年（Chrome 133 / Safari 17.4 / Firefox 135），旧浏览器必须走 `isUserVerifyingPlatformAuthenticatorAvailable()` 兜底。
12. 通过第三方翻译或二手博客得到的「NIST 要求 8 位」多为 63B-3 口径，本资产以 63B-4 为准并在 §4 标注差异。
13. 推送确认的「数字匹配」为行业实践（Microsoft Authenticator 等），本资产不给具体超时数值。
14. 「记住此设备 30 天」「验证链接 15–60 分钟」「重发 30–60 秒」均为工程约定，无规范出处，已在正文标注。
15. GitHub star/许可为 2026-11-14 匿名 API 快照（60 次/小时配额），`NOASSERTION` 一律按红灯处理。
