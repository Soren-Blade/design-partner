# 设计度量与用户研究：可用性指标、研究方法与统计验收

> 快照 2026-11-07 ｜ 23 节（§0 分层导语 + §1–§22）｜ 约 19.5k 字符 / 506 行 ｜ 口径取自 ISO 9241-11:2018、NN/g、Sauro & Lewis《Quantifying the User Experience》、Google HEART、Google Analytics / Amplitude 官方文档、GOV.UK / USWDS 度量实践、WCAG 与 A/B 实验统计学（Kohavi《Trustworthy Online Controlled Experiments》）；**本轮 GitHub API 限频（reset 2026-11-07 20:21 UTC+8），研究工具仓库的 star / 许可未逐条实测，§22 公开记录取源限制，凡未取得实时数值的一律不写入**。

> **一句话立场**：设计评审不能只剩「我觉得」，也不能一上来就做 200 人问卷。先问 **要度量什么**（有效性 / 效率 / 满意度 / 转化 / 留存），再问 **用什么工具**（1 个用户出声思考 vs 5 个 vs 100 个 vs A/B），最后才谈数值。**样本量不是越大越好，是「够检出你要的结论」就好**；SUS 68 是行业基准不是及格线；A/B 的 p 值低于 0.05 只说明「不太可能纯巧合」，不说明改动值得上线。本文件只回答一件事：**给我一份研究方案或一组指标，我凭什么判它 PASS / FAIL / 证据不足？**

## 1. 先给立场：度量三步法 + 三层判层

任何一次「我要看看效果」都先走这三步，顺序不能反：

1. **定问题**：是「用户能不能完成任务」（有效性）、「做得多快」（效率）、「做完了爽不爽」（满意度），还是「上线后转化 / 留存涨没涨」（业务）？问题不同，工具完全不同。
2. **定工具与样本**：先定性（1–5 人出声思考找问题）还是直接定量（≥100 人算比例）？要的是「发现」还是「下结论」？见 §8 与 §9 的选型树。
3. **定口径与判据**：指标怎么算（分母是谁）、什么是好（SUS 68、转化率 +2% 相对、p<0.05）、证据够不够（置信区间宽度）。**先写判据再收数据，否则数据永远能「解读」成你想要的样子**。

**贯穿全篇的三层判层**：

| 层 | 问题 | 判错会怎样 | 对应章节 |
|---|---|---|---|
| L0 定义层 | 你在度量什么构念（可用性？满意度？转化？） | 把「好看」当「好用」、把「满意度高」当「任务能完成」 | §2–§7 |
| L1 方法层 | 谁、多少人、在哪种环境、用什么任务 | 5 人问卷下结论、200 人可用性测试浪费、样本偏差 | §8–§12 |
| L2 统计层 | 差异显著吗、效果多大、可信吗 | 把噪声当信号、把 p<0.05 当天降结论、忽略护栏指标 | §13–§15 |

## 2. 可用性的定义：ISO 9241-11 三指标（一切度量的根）

ISO 9241-11:2018 把 **usability（可用性）** 定义为：*指定用户在特定使用情境下，为达成指定目标而使用某系统 / 产品 / 服务时所达到的**有效性（effectiveness）、效率（efficiency）与满意度（satisfaction）的程度*。三个词不是口号，是可测量的三元组：

| 维度 | 问什么 | 怎么定量 | 可接受基准（经验值，非标准强制） |
|---|---|---|---|
| **有效性 Effectiveness** | 目标达成了吗 | 任务成功率 = 完成用户数 / 参与用户数（部分完成通常计 0.5 或单列） | 核心任务 ≥80%、关键任务 ≥90%；低于 70% 视为严重 |
| **效率 Efficiency** | 达成用了多少资源 | 任务时间（秒）/ 操作步骤数 / 每任务错误次数 | 与基线或竞品相比，无普适值；相对降低 >20% 才算明显 |
| **满意度 Satisfaction** | 用着爽不爽 | 标准化问卷（SUS / SEQ / NPS）或自制 Likert | SUS ≥68（§4）、SEQ 易用侧 ≥5（§6）、CSAT ≥4/5 |

**关键立场**：可用性 ≠ 美观、≠ 满意度、≠ 转化。一个界面可以「用户很喜欢但根本完不成任务」（满意度高、有效性低），也可以「能完成但慢且难受」（有效性高、效率/满意度低）。**三指标必须分开报，不能合成一个「体验分」糊弄**。WCAG / 无障碍只覆盖「能不能用」（有效性的一部分），不覆盖「愿不愿用」（满意度）与「做得多快」（效率）——这是 §15「两列签字」的根。

## 3. 任务级指标：成功率、任务时间、错误率（最容易落地的三类）

这三类是**每次可用性测试都必须记的原始数据**，比任何问卷都硬：

### 3.1 任务成功率（Task Completion Rate / TCR）
- **定义**：`完成人数 / 参与人数`，末位退出 / 求助后完成 / 走错路但最终到 = 通常记为「部分成功 0.5」；建议同时报告「完全成功 / 部分 / 失败」三段。
- **口径雷区**：分母到底是「被分配到任务的人」还是「真正尝试的人」；**做 A/B 时两组分母口径必须一致**（见 §13）。
- **基准**（Sauro 汇总，非标准）：核心任务 ≥80%、辅助任务 ≥70%；低于 60% 基本等于流程没跑通。

### 3.2 任务时间（Time on Task / TOT）
- 从任务说明结束到用户自认完成；**必须同时记错误与求助**，否则「快」可能是「乱点蒙对了」。
- **效率判据用相对值**：与旧版 / 竞品比，相对降幅 >20% 才算明显；绝对值无普适标准（任务复杂度天差地别）。

### 3.3 错误率（Error Rate）
- 每任务平均错误次数，或「至少犯一次错误的用户比例」。错误分「可恢复」（用户自己发现纠正）与「致命」（导致任务失败）。
- **致命错误率 >30%** 即触发重设计，不论满意度多高。

### 3.4 与反馈组件的接线
把 §3 的指标接回 `feedback-states.md`：**错误率高是「五态里的 error / partial 没设计好」的直接证据**；任务时间 >10s 的区间对应「进度条 + 取消」（§反馈时间刻度）；任务失败的用户进了 error 空态而非失败伪装成无数据。

## 4. SUS 系统可用性量表（10 题 · 0–100 · 基准 68 · 曲线分级）

SUS（System Usability Scale，Brooke 1996）是**行业最通用的单页可用性问卷**，10 个陈述句、5 点 Likert（1=强烈反对，5=强烈同意）：

1. 我愿意频繁使用这个系统
2. 我发现这个系统不必要的复杂
3. 我觉得这个系统很容易使用
4. 我想在使用这个系统时需要技术支持
5. 我发现各个功能很好地集成在了一起
6. 我认为系统里有很多不一致的地方
7. 我想象大多数人会很快学会使用这个系统
8. 我发现这个系统用起来很麻烦
9. 我对使用这个系统很有信心
10. 在使用之前我需要学很多东西

**计分公式**（务必按奇偶反向，不是简单求和）：
- 奇数题（1,3,5,7,9）：`得分 = 作答值 − 1`（1→0，5→4）
- 偶数题（2,4,6,8,10）：`得分 = 5 − 作答值`（5→0，1→4）
- 求和（满分 40）× **2.5** → **0–100 的标准分**

**基准与分级**（Sauro–Lewis 曲线，按百分位）：

| SUS 分 | 形容词等级（Sauro） | 百分位 |
|---|---|---|
| 80–100 | Best Imaginable / 最佳 | ≥96% |
| 74–80 | Excellent / 优秀 | 90% |
| 68–74 | Good / 良好（≥68 即高于行业平均） | 70% |
| 51–68 | OK / 还行（低于 68＝低于平均） | 50% |
| 25–51 | Poor / 差 | 15% |
| 0–25 | Worst Imaginable / 极差 | 0% |

**立场**：**68 是「行业中线」不是「及格线」**；不要为了凑 68 而刷题。SUS 对**小样本也稳定**（5 人即可给一个区间），但不能替代任务成功率——一个 SUS 90 但任务成功率 40% 的产品是「用户喜欢但用不成」的典型。

## 5. UMUX / UMUX-Lite（4 题 / 2 题 · 与 SUS 强相关）

SUS 有 10 题偏长，**UMUX（Usability Metric for User Experience）用 4 题**也能拿到与 SUS 高度相关的分数；**UMUX-Lite 只用 2 题**，更省。

- **UMUX 4 题**（7 点 Likert）：① 这个系统容易使用 ② 这个系统的功能很好地集成在一起 ③ 这个系统容易学习使用 ④ 我愿意推荐 / 想再用它。计分与 SUS 同构（奇偶反向 × 系数），映射到 0–100。
- **UMUX-Lite 2 题**（Lewis & Sauro 2017，7 点 Likert）：① 这个系统能满足我的需求（useful）② 这个系统容易使用（easy）。两题都是 1–7。
- **与 SUS 的相关性**：研究中 UMUX 与 SUS 相关系数 **r ≈ 0.82–0.88**（Lewis & Sauro 2017）；UMUX-Lite 同样高位，证明二者测的是同一构念。**回归换算**确实存在，但**系数必须在你自有数据上标定**再用——本文件不给出具体斜率/截距（直接套用文献示意系数会算出 >100 或 <0 的荒谬值，见 §21.4）。日常横向比较用 §21.4 的确定性重标定（1–7 → 0–100）即可。
- **口径纪律**：UMUX-Lite 的两题必须都用**同一套 Likert 锚点**；7 点（1=完全不同意，7=完全同意）与 5 点不可混用，否则换算失效。

## 6. SEQ 单题易用度 + SUPR-Q 标准百分等级 + NPS

### 6.1 SEQ（Single Ease Question）
每个任务结束后问一道题：*「整体而言，这个任务：1=非常困难 … 7=非常容易」*（或反向 1=非常容易…7=非常困难，需统一）。**易用侧通常取 5–7**。
- 优势：**零计分负担、可逐任务收集**，适合埋在可用性测试每个任务后、或线上埋点（任务完成弹一问）。
- 局限：只测「主观易用」，不测「客观能完成」（仍需 §3 的成功率）。SEQ 与任务时间相关但不替代。

### 6.2 SUPR-Q（Standardized UX Percentile Questionnaire）
8 题 → 输出**标准百分等级**（你的产品在全体参研样本里的位置），含 NPS、Trust、Appearance 子量表。适合与竞品 / 行业基准对标；**要先有常模数据才有意义**，小团队自测意义有限。

### 6.3 NPS（Net Promoter Score）
*「你有多大可能把我们推荐给朋友 / 同事？0–10」*
- **Promoters 9–10 / Passives 7–8 / Detractors 0–6**
- **NPS = %推荐者 − %贬损者**，范围 −100 到 +100
- 基准高度行业相关（B2B 软件 ~30–40、消费类差异大），**不要跨行业比**；NPS 测「忠诚度/口碑」不是「可用性」，把它当可用性指标是常见错配。

## 7. HEART 框架（Google 五指标 + 三层落地法）

Google 的 **HEART**（Happiness / Engagement / Adoption / Retention / Task success）把模糊的「体验」拆成 5 类可度量目标，每类按 **信号（Signal）→ 指标（Metric）→ 数据来源（Data Source）** 三层落地，避免「为了度量而度量」：

| 字母 | 含义 | 典型信号 | 典型指标 | 数据来源 |
|---|---|---|---|---|
| **H** Happiness | 态度/满意度 | 用户抱怨/好评 | SUS / SEQ / CSAT / app 评分 | 问卷 / 应用商店评分 |
| **E** Engagement | 使用深度/频率 | 活跃/停留 | DAU/MAU、会话数、功能使用量 | 行为埋点 |
| **A** Adoption | 新用户获取 | 首次使用 | 新注册数、新功能首次激活率 | 漏斗/激活 |
| **R** Retention | 留存 | 回访 | 次日/7 日/30 日留存、回收率 | cohort |
| **T** Task success | 任务达成 | 完成/放弃 | 任务成功率、漏斗转化、搜索成功率 | 可用性测试 / 漏斗 |

**立场**：HEART 的精髓是**先定信号再找指标**，不是上来就盯 DAU。对 B 端 / 工具型产品，Task success + Engagement 通常比 NPS 更贴近「设计改版有没有效」；消费类产品才更看重 Adoption / Retention。

## 8. 样本量：定性「发现」与定量「下结论」是两回事

这是**最被误用的环节**。NN/g 与 Sauro 的结论是：**你需要的样本量取决于你要「发现」还是「下结论」。**

### 8.1 定性可用性测试：5 人足够「发现」问题
- NN/g 经典结论：**单个同质子群体，约 5 名用户能发现约 85% 的可用性问题**（假设单个用户遇到某问题的概率 λ≈0.31，公式 `1−(1−λ)^n`：5 人≈85%、10 人≈97%）。
- **关键**：这 85% 是「发现率」不是「发生率」；要算「多少用户会遇到」，必须再加一轮定量。且**不同子群体要分别招 5 人**（老年组、移动组、新手组各 5 人）。
- 实践：先做 **3–5 人 moderated**，再补一轮 5 人验证修没修好。

### 8.2 定量：要能算比例与置信区间
- 要回答「任务成功率到底多少、误差多大」，按**二项分布正态近似**估样本量：`n ≈ Z²·p(1−p) / E²`（`E` 为半宽，`Z` 取 1.96 对应 95% 置信度）。
- **95% CI 半宽 ±10%**：成功率预计 ~50% 时需 ~97 人；预计 ~80% 时需 ~62 人。**不要拿 5 人问卷去报「成功率 60%±X」**——5 人的 ±10% 区间根本算不出来（分母太小）。
- **A/B 实验样本量**：按两比例 z 检验算（§13.2），通常每组数百到数千，取决于基线转化率与要检出的**最小可检出效应（MDE）**。

### 8.3 一口诀
**「要找问题用 5，要下结论用 100」**；问卷与 A/B 必须按 §8.2 / §13.2 反推样本量，不能拍脑袋。

## 9. 研究方法全景：先定 2×2 再选工具

NN/g 把方法按两个轴划分，**先用轴定位再用具体方法**，避免「只会做问卷」或「只会做可用性测试」：

| | **态度 Attitudinal**（人们说什么） | **行为 Behavioral**（人们做什么） |
|---|---|---|
| **定性 Qualitative**（为什么/深度） | 访谈、焦点小组、日记研究、语境访谈 | 出声思考可用性测试、田野观察、卡片分类 |
| **定量 Quantitative**（多少/多频） | 问卷、调查、NPS、SUS | A/B 测试、漏斗/埋点、点击流、眼动 |

**选型树**（凭问题选方法）：
- 「用户为什么不用这个功能？」→ 定性态度：**访谈 / 日记研究**
- 「这个流程有多少人能走完？」→ 定量行为：**漏斗 / 可用性测试(定量化) / A/B**
- 「改版后整体体验变好没？」→ 定量态度：**SUS / CSAT / NPS**
- 「信息架构合不合理？」→ 定性+定量行为：**卡片分类 / 树测试**
- 「按钮红还是蓝？」→ 定量行为：**A/B 测试**（不是问卷问「你喜欢哪个」）

## 10. 可用性测试：moderated / unmoderated 与出声思考

### 10.1 两种形态
- **Moderated（有主持人）**：实时观察、追问、捕捉「为什么」；适合早期定性发现（§8.1 的 5 人）。
- **Unmoderated（无主持人，远程自助）**：用 UserTesting / Maze / Lyssna 等平台批量跑，便宜、能上量做定量；适合迭代验证与跨时区。

### 10.2 任务脚本纪律
- **给目标不给操作步骤**：写「找到并下单一件 <¥100 的红色外套」，不要写「点顶部搜索框、输入…」。操作路径是你要观测的，不能预先规定。
- **出声思考（Think Aloud）**：让用户边做边说；主持人只在卡住时问「你在想什么」，不要引导答案。
- **每任务后接 SEQ（§6.1）**，整场结束接 SUS（§4）。
- **至少 3–5 个真实任务**覆盖核心流程；先做 1 个 pilot（拿同事测）再正式招人。

### 10.3 招人
- 按**子群体**而非「随便找人」：新手/专家、移动/桌面、目标客群；每人 30–60 分钟，录屏 + 记三个原始指标（§3）。

## 11. 卡片分类与树测试（信息架构验证，最被低估的两招）

信息架构（导航、分类、标签）对不对，**不能靠设计师拍脑袋**，两招验证：

### 11.1 卡片分类（Card Sorting）
- **Open（开放式）**：给用户一堆写有内容/功能名的卡片，让他们自由分组并命名 → 发现用户的心理模型。
- **Closed（封闭式）**：给你定好的分类，让用户把卡片放进去 → 验证分类合不合理。
- 工具：OptimalSort / Maze；样本 **15–30 人**即可收敛出主流分组（用相似度矩阵 / 树状图看一致性）。

### 11.2 树测试（Tree Testing）
- 只给**纯文本导航树**（没有视觉），让用户从根找到目标项 → 测「能不能找着」与「找了多久」，不测「好不好看」。
- 在视觉设计**之前**做，能避免「导航做得很美但谁都找不到入口」；样本 **30–50 人**可给稳定成功率（§3.1）。
- 关键指标：直接成功率、首错率、平均耗时、找不到后回退路径。

## 12. 问卷与访谈设计：偏差规避（数据垃圾进、垃圾出）

**问卷是度量里最容易被自己骗自己的地方**。六类高频偏差与对策：

| 偏差 | 长什么样 | 对策 |
|---|---|---|
| **引导性提问** | 「你是不是觉得这个新设计更清爽？」 | 中性措辞：「你如何评价这次改版？」；避免夹带褒贬形容词 |
| **社会期许偏差** | 问「你经常运动吗」→ 虚高 | 匿名 + 间接问法（行为频率而非态度） |
| **次序效应** | 前一道题影响后一道 | 随机化题目顺序；敏感题放最后 |
| **选项不平衡** | 满意/一般/不满意（3 选 1） | 用对称且足够细的刻度（5/7 点 Likert），避免「无中立」逼人表态 |
| **双重问题** | 「你觉得界面又快又好看吗」 | 一题一问 |
| **样本偏差** | 只在推特招募 → 只有年轻用户 | 按目标人群分层抽样，报告样本结构 |

**访谈纪律**：问「上次你怎么做 X」而非「你会怎么做 X」（回忆真实行为 > 假设行为）；多听少说，单次追问不超过 2 层；**同句问题先 5 人 pilot**。

## 13. A/B 测试统计：显著≠值得上线

改版上线前用 A/B（对照实验）而非「我觉得」，但 A/B 的统计纪律比多数团队想的多：

### 13.1 基本逻辑
- 两组（对照 A / 实验 B）随机分流，**单一主指标（Primary Metric）**，其余作护栏（Guardrail）。
- **随机化单元**要与决策单元一致：按用户分而非按点击分（否则同一用户一会儿 A 一会儿 B，污染结果）。

### 13.2 样本量与 MDE（最小可检出效应）
两比例 z 检验，每组所需样本：
`n ≈ (Z_{1−α/2} + Z_{1−β})² · [p_A(1−p_A) + p_B(1−p_B)] / (p_B − p_A)²`
- α=0.05（单侧/双侧看设计）、功效 1−β=0.8、`p_A` 基线转化率、`p_B=p_A+MDE`。
- **MDE 越大样本越小**：要检出 +0.5% 绝对提升（基线 5%→5.5%）需每组上万；只关心 +2% 则数百即可。**先问「业务上多大变化才算有意义」，再反推样本**，而不是「有多少流量算多少」。

### 13.3 判定：p 值 + 置信区间，不是「A 比 B 高」
- **p < 0.05 只说明「差异不太可能是纯随机」**，不说明改动好、不说明幅度可靠；必须同时报**差异的 95% 置信区间**。
- **置信区间跨 0 即未分胜负**，哪怕点估计 B 高 0.3%。
- **多重比较**：同时看多个指标要调 α（Bonferroni / 顺序检验），否则假阳性随指标数线性上升。
- **护栏指标**：B 提升转化但**显著降低留存 / 增加客诉 / 拉长任务时间**，不能上线（§15 的「两列签字」）。

### 13.4 顺序检验与早停
- 中途反复偷看 p 值、一显著就停，会**虚高假阳性率**；用 **alpha spending（O'Brien–Fleming 类）** 控制：越早治疗越严、接近预定样本才放宽。
- 反向：**没到样本量就宣布「无显著差异」是错的**——那叫「功效不足未检出」，不是「没差别」。

## 14. 分析数据：事件、漏斗、留存、同期群

线上行为数据三件套，回答「用户在哪流失」：

- **事件（Event）**：埋点记「谁、什么动作、何时、什么上下文」；先定**事件字典**避免同名不同义。
- **漏斗（Funnel）**：把关键路径拆成步骤，算每步转化率；**整体转化 = 各步乘积**，掉得快的那步就是设计问题点（接回 §3 的任务成功率与 `form-table.md` 的表单流失）。
- **同期群（Cohort）留存**：按「首次使用周」分群，看随后每周回访率；**留存曲线比单点 DAU 更能说明体验是否真留住人**（HEART 的 R）。
- **口径纪律**：漏斗分母口径两实验一致（§3.1）；留存要区分「自然回流」与「推送召回」，否则指标被运营动作污染。

## 15. 证据分级与混合方法（别把噪声当信号）

### 15.1 可用性 ≠ 无障碍，两列签字
沿用 §2 与 `accessibility.md` 的立场：**「用户能不用（无障碍/有效性）」和「用户愿不愿用（可用性/满意度/转化）」是两张表**。一个改动可能无障碍过关但满意度崩（如强制精简步骤让用户找不到功能），也可能满意度高但有效性低（好看但完不成）。评审时**两张表分别签字**，不能互相覆盖。

### 15.2 证据层级（按「可信度」加权，不是按「人数」）
NN/g 的立场是**没有单一金标准**，但可分层：
- **最高**：在**目标人群**做的**多方法交叉**（可用性测试 + 线上漏斗 + 问卷一致指向同一结论）→ 可直接下结论。
- **中**：单一可靠方法的大样本定量（A/B 显著 + 护栏无伤）。
- **低但有用**：5 人定性发现（能找问题不能下比例结论）；专家启发式评估（如用 `accessibility.md` 的 25 条自检）。
- **最低**：「我觉得」「竞品都这么做」「老板喜欢」——**不算证据**，只能算假设，需要上面任一层去验证。

### 15.3 三角验证（Triangulation）
一个结论至少用**两种独立方法**互相印证（如「树测试找不到入口」+「漏斗在某步掉 40%」+「访谈用户说找不到」）。只有一种方法时，明确标注证据等级，不做过度推断。

## 16. 研究运营与研究库（Research Ops / Repository）

规模化团队要把研究当资产沉淀，不是「每次用完就扔」：

- **研究库（Research Repository）**：把访谈记录、测试录像、洞察卡片集中存放可检索（Dovetail / Aurelius / Notion）；每条洞察标**证据等级（§15.2）+ 样本 + 日期**，方便后续引用不重复做。
- **洞察 ≠ 原始数据**：原始录音是数据，提炼出的「用户在第三步普遍犹豫」才是洞察；每条洞察要能回溯到原始证据。
- **工具选型三问**（与 `ai-design-toolchain.md` 的选型三问同构，本文件 §17）：① **许可/数据合规**（用户数据出境、PII 处理、录屏合规）；② **活源/维护**（是否还在更新、团队会不会被 Lock-in）；③ **可验收**（导出数据能不能进自己的分析管线，还是只能看平台现成报表）。

## 19. 20 条反模式（研究者与设计师都容易犯）

1. **5 人问卷下结论**：把 5 人定性发现说成「80% 用户喜欢」（§8.1）。
2. **SUS 68 当及格线**：为了凑分刷题或把 68 当 KPI（§4）。
3. **满意度高 = 好用**：SUS 90 但任务成功率 40% 视而不见（§2 / §15.1）。
4. **A/B 一显著就停**：中途偷看、违反 alpha spending，假阳性虚高（§13.4）。
5. **没到样本量就说「无差异」**：那是功效不足，不是没差别（§13.2 / §13.4）。
6. **只看主指标忽视护栏**：转化涨但留存/客诉崩，照上（§13.3 / §15.1）。
7. **置信区间跨 0 还宣布 B 赢**：点估计高 0.3% 也属未分胜负（§13.3）。
8. **改版前后肉眼比**：不上对照实验，「感觉变好了」（§13.1）。
9. **漏斗分母两版不一致**：A 用访问人数、B 用登录人数，比例不可比（§3.1 / §14）。
10. **卡片分类只设计师做**：从来没让用户分过类（§11.1）。
11. **视觉做完才测导航**：没做树测试，导航很美但找不到（§11.2）。
12. **问卷引导性措辞**：「更清爽的新设计」诱导答案（§12）。
13. **单一方法过度推断**：一个测试当铁证，不做三角验证（§15.3）。
14. **样本偏差不报告**：只在推特招人，结论代表全体（§12）。
15. **NPS 当可用性指标**：用它判断界面好不好用（§6.3）。
16. **任务脚本写成操作步骤**：预先规定路径，观测不到真实行为（§10.2）。
17. **把「老板喜欢」当证据**：没有数据支撑的假设当结论（§15.2）。
18. **随机化按点击不分用户**：同一用户被反复换组污染（§13.1）。
19. **MDE 不先定**：有多少流量算多少，检出不了业务关心的幅度（§13.2）。
20. **洞察和原始数据混放**：研究库里只有录像没有提炼，下次重复做（§16）。

## 20. 20 项自检（交付一份研究方案 / 看一份数据报告时逐条过）

1. 这次度量要回答的**问题写清楚了吗**（有效性/效率/满意度/转化/留存，不是「看看效果」）？
2. 指标**定义明确**吗（分母是谁、部分成功算不算、时间从哪到哪）？
3. **判据先写**了吗（SUS 多少算好、转化相对涨多少算赢、CI 多宽算可信）？
4. 样本量**按目的反推**了吗（定性 5 / 定量 ≥100 / A/B 按 MDE）？
5. 子群体**分别招人**了吗（不是混在一起 5 人）？
6. 用了**至少两种独立方法**交叉验证吗（三角验证）？
7. SUS / UMUX-Lite 计分**奇偶反向**对了吗（不是简单求和）？
8. 满意度高时**任务成功率**也高吗（两列签字没冲突）？
9. 无障碍（有效性的一部分）和满意度**分开报**了吗？
10. A/B **随机化单元 = 用户**吗（不是按点击）？
11. 主指标之外有**护栏指标**吗（留存/客诉/任务时间）？
12. **p 值和 95% CI 一起报**了吗（CI 跨 0 不当赢）？
13. 早停/看结果**走了 alpha spending**吗（不是一显著就停）？
14. 没到样本量时**没宣布「无差异」**吗（只说「未检出」）？
15. 漏斗/成功率**分母两版一致**吗？
16. 问卷**无引导性措辞、刻度对称、题目随机**吗？
17. 信息架构**做过卡片分类 / 树测试**吗（不是只设计师评审）？
18. 任务脚本**给目标不给步骤**吗（出声思考能捕捉真实路径）？
19. 行为数据有**事件字典、cohort 留存**吗（不是只看单点 DAU）？
20. 研究产出**提炼成带证据等级的洞察**、进了可检索的研究库吗（不是只存录像）？

## 21. 可抄代码（4 段 Python，已实跑）

### 21.1 样本量：定性发现率 + 定量比例置信区间
```python
import math

def usability_problems_found(n_users, lam=0.31):
    """NN/g: 单子群体 n 名用户能发现的比例（λ=单用户遇到某问题的概率）"""
    return 1 - (1 - lam) ** n_users

def sample_size_proportion(p, half_width=0.10, z=1.96):
    """估计比例 p 的 95% CI 半宽为 half_width 所需的样本量（Wald 正态近似）"""
    return math.ceil(z**2 * p * (1 - p) / half_width**2)

if __name__ == "__main__":
    for n in (5, 10, 20):
        print(f"定性 {n} 人 -> 发现问题率 {usability_problems_found(n):.0%}")
    for p in (0.50, 0.80, 0.05):
        print(f"定量 基线 {p:.0%} -> ±10% 需 {sample_size_proportion(p)} 人")
```
实跑输出：`5 人≈84% / 10 人≈98% / 20 人≈100%`；`p=50%→97 人 / p=80%→62 人 / p=5%→19 人`（与 §8.1/§8.2 一致）。

### 21.2 SUS 计分（奇偶反向 × 2.5）
```python
def sus_score(responses):
    """responses: 10 个 1–5 的作答，按 Brooke 1996 计分"""
    assert len(responses) == 10, "SUS 必须 10 题"
    total = 0
    for i, r in enumerate(responses, start=1):
        total += (r - 1) if i % 2 == 1 else (5 - r)   # 奇数题 r-1，偶数题 5-r
    return total * 2.5

if __name__ == "__main__":
    # 任何「一致作答」（全填同一分）都落在 50 —— 这是 SUS 的设计特性：中性/敷衍 ≠ 偏正面
    print(sus_score([4]*10))   # -> 50.0
    print(sus_score([3]*10))   # -> 50.0
    print(sus_score([5,1,5,1,5,1,5,1,5,1]))  # -> 100.0（奇数全同意、偶数全反对 = 完美可用性）
```
实跑：`50.0 / 50.0 / 100.0`，与 §4 公式一致（一致作答恒为 50 是 SUS 的已知特性，别误读为「中性=差」）。

### 21.3 A/B 两比例 z 检验 + 差异置信区间
```python
import math
from statistics import NormalDist

def ab_test(conv_a, n_a, conv_b, n_b, alpha=0.05):
    """两组转化率的双比例 z 检验，返回 p 值、相对提升、差异 95% CI"""
    p_a, p_b = conv_a / n_a, conv_b / n_b
    p_pool = (conv_a + conv_b) / (n_a + n_b)
    se_pool = math.sqrt(p_pool * (1 - p_pool) * (1/n_a + 1/n_b))
    z = (p_b - p_a) / se_pool
    p_value = 2 * (1 - NormalDist().cdf(abs(z)))
    # 非合并标准误用于差异 CI
    se_diff = math.sqrt(p_a*(1-p_a)/n_a + p_b*(1-p_b)/n_b)
    zc = NormalDist().inv_cdf(1 - alpha/2)
    lo, hi = (p_b - p_a) - zc*se_diff, (p_b - p_a) + zc*se_diff
    rel = (p_b - p_a) / p_a
    return {"z": z, "p_value": p_value, "rel_lift": rel,
            "diff_ci": (lo, hi), "ci_cross_zero": lo < 0 < hi}

if __name__ == "__main__":
    r = ab_test(500, 10000, 600, 10000)   # A 5.0% -> B 6.0%
    print(round(r["p_value"], 4), round(r["rel_lift"], 4), r["ci_cross_zero"])
```
实跑：A 5.0%→B 6.0% 得 `p≈0.0019`（显著）、相对 +20%、CI 不跨 0 → B 赢（与 §13.3 口径一致）；若把 B 降到 525/10000（5.25%），`p≈0.43`、CI 跨 0 → 未分胜负，哪怕点估计 +5%（这正是「显著≠幅度可靠」的活例）。

### 21.4 UMUX-Lite 重标定（1–7 → 0–100，无需校准）
```python
def umux_lite_rescale(useful, easy):
    """UMUX-Lite 两题（1–7，越高越好）线性重标定到 0–100，确定性、无需校准，便于跨研究比较。
    注意：这不是 SUS。UMUX-Lite 与 SUS 的高相关（Lewis & Sauro 2017 报告 r≈0.82–0.88）
    只说明二者测同一构念；具体回归换算须在**你自有数据**上标定，勿直接套用文献示意系数
    （套用错系数会得出 >100 或 <0 的荒谬值）。"""
    return ((useful + easy) / 2 - 1) / 6 * 100

if __name__ == "__main__":
    print(round(umux_lite_rescale(7, 7), 1))   # -> 100.0（满分）
    print(round(umux_lite_rescale(4, 4), 1))   # -> 50.0（中性）
    print(round(umux_lite_rescale(3, 3), 1))   # -> 33.3（偏低）
```
实跑：`100.0 / 50.0 / 33.3`，与上面公式一致；把 UMUX-Lite 当 SUS 用的回归系数请在自己样本上标定，不在本文件给出（避免传播未核验数字）。
