# 数值口径单点（Numeric Truth）

> 一句话：同一个数只能有一个裁决源。这份表是设计知识库的「数值宪法」——正文只解释「为什么」和「这里该怎么用」，不再各自复述一遍数字。

**读法**：写规范、评审、交付前先查本表；正文里看到与本文冲突的数字，以本文为准，并回头改正文。新增数值先加进本表，再写进 references。

---

## 0 · 立场：一个数，一个裁决源

设计文档里最常见的坏味道，不是数字本身错，而是**同一个数字在三个文件里有三个版本**：行高在 A 文件写 1.5、B 文件写 1.7–1.8、C 文件写「推荐 1.6–1.8」；点击尺寸在一处引 WCAG 的 24px、另一处引 M3 的 48dp。读者不是专家时，只能挑一个自己看着顺眼的——于是等于没有规范。

本文件的立场只有五条：

- **唯一裁决源**：同一个数在本知识库内只有一个权威出处，就是这张表。其他 references 与本文冲突时，一律以本文为准。
- **先改表，再改文**：要动一个口径，必须先改本表并写清理由与来源，再同步引用方。禁止先在某个单文件里「顺手调一下」。
- **本文件不发明数值**：表里的每个裁决值都能追到法条、官方设计系统、一手实测或明确标注的经验值。没有来源的数字不进表。
- **本文件管「数」，不管「做法」**：为什么中文行高比拉丁宽、justify 在什么条件下可用、combobox 怎么接线，仍由各专题文件展开；本文只给那个最终的数。
- **经验值必须自曝身份**：凡是「多数项目好用、但没有强制来源」的值，表里统一标「经验值」，不许伪装成法条。

> 反过来说：如果你在某个 reference 里看到一个数，却在本表查不到，那它要么该补进本表，要么就该改成「见 numeric-truth §1」并删掉重复数值。

### 1.5 表外的高频误用

- **把区间当默认**：写「1.6–1.8」却不给推荐值，实现者会取 1.6，长文偏挤。本表统一给「推荐 1.7」。
- **把库默认当设计值**：Ant 的 14px 主字号是 B 端信息密度选择，不是所有产品的正文起点。
- **拿单点数字跨场景复用**：48dp 是 M3 的触控建议，不等于桌面端每个按钮都要 48px 高。
- **用「最佳实践」当来源**：本表不接收没有年份与出处的「最佳实践」。
- **在正文里复述整张表**：正文只留一句「见 numeric-truth §1」+ 该文件特有的判断，复述三遍就是下一个矛盾的种子。

## 2 · 六条口径纪律

### 2.1 先分清四种数

| 类型 | 定义 | 写法 | 例子 |
|---|---|---|---|
| **法条** | 标准/法规里的 MUST 或 SHOULD，可验收 | 「必须 / 应」+ 条款号 | WCAG 2.5.8 的 24×24 底线 |
| **设计值** | 本库为多数场景选定的默认值 | 「默认 / 推荐」+ 来源 | 中文正文行高 1.7 |
| **库默认** | 某个设计系统/框架的出厂值 | 「某库默认」+ 版本 | Ant 主字号 14px |
| **经验值** | 多数项目好用，但无强制来源 | 明确标注「经验值」 | 搜索建议 8–10 条 |

四者混写，读者就无法判断「能不能改」。**同一个句子里禁止把经验值写成 MUST。**

### 2.2 引用必须带类型

写「行高 1.5」是不够的，要写「拉丁 UI 行高 1.5（设计值，M3 2024）」。类型是给读者的许可边界：法条不能破，设计值可换但要说明，库默认可覆盖，经验值可调。

### 2.3 不得把 WCAG 24px 当「推荐点击尺寸」

WCAG 2.2 SC 2.5.8 的 24×24 CSS px 是 **AA 底线**（Target Size Minimum），不是推荐值；推荐值是 44×44（SC 2.5.5 AAA 与 Apple HIG 的交集）。把底线写成「推荐 24px」会让整个产品落在及格线上。

### 2.4 不得把 M3 的 48dp 当普适法条

48dp 是 Material 生态的触控建议，不是跨平台法条，也不是桌面鼠标场景的硬指标。跨端产品应写「触控 ≥44，Material 端 48，桌面可 32–44」，而不是一句「全部 48」。

### 2.5 冲突裁决顺序

**法条 > 用户实测 > 本表 > 单文件。**

- 法条优先：WCAG 的 4.5:1 不能被「品牌色好看」推翻。
- 用户实测其次：有本产品可用性测试数据时，实测优先于本表的经验值，但必须把数据写进变更记录。
- 本表再次：没有法条与实测时，按本表。
- 单文件最后：任何 reference 里的局部数值，与前三者冲突即失效。

### 2.6 改口径的硬流程

1. 在本表找到该行，写清「为什么改、依据是什么、影响哪些文件」。
2. 改本表裁决值，并在 §4 变更记录加一行。
3. 用 grep 找出所有引用方，逐处改成「见 numeric-truth §1」+ 本文件特有判断。
4. 跑一遍 §5 自检，确认没有留下旧数值的孤岛。
5. 不允许「只改单文件、不改表」——那正是这轮审计要修的病。

### 3.3 正文写法对照

- **好**：「中文正文行高用 1.7（见 numeric-truth §1）；原因是汉字字面率高、同字号视觉更满，需要比拉丁略松。」
- **坏**：「中文行高 1.6–1.8，推荐 1.7；小字 1.5–1.6；拉丁 1.5；长文 1.4–1.6……」——把表抄一遍，下次改口径必漏。
- **好**：「justify 只在满足三个条件时可用（见 numeric-truth §1）；本文件负责解释这三个条件为什么缺一不可。」
- **坏**：在一个文件说「中文 justify 推荐」，另一个文件说「justify 是硬禁」。

### 3.4 引用格式

统一写 `（见 numeric-truth §1.x）`，x 取 1.2 / 1.3 / 1.4。不要写「见上文」「见规范」，也不要复制表格行号——表会增行，行号会漂。
