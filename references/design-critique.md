## 0. 先分清：本文件补什么

`handoff-collaboration.md` §9 已经把"一场评审会怎么开"讲清楚了（30 分钟、2 正 1 改、Presenter/Critiquer 角色、三前提）。本文件补的是它没展开的 **评审手艺与评判尺子**：

- 怎么把"我觉得"翻译成"挂在目标上的、可被反驳的反馈"（§3）
- 怎么接收反馈而不辩护（§4）
- 怎么把"好不好"变成可讨论的框架，而不是各说各话（§6）
- 15 条反模式 + 20 项自检 + 4 段可抄模板（§7 / §10 / §11）

记住：**评审是发现问题，不是现场改稿**；决策要留痕，否则两周后被"我觉得不好看"推翻。

---

## 1. 两种评审，别混在一场会

| | **Standalone critique（同行评审）** | **Design review（决策评审）** |
|---|---|---|
| 目的 | 让设计更好，开放探索 | 做决策、审批、对齐 |
| 谁主导 | 同伴轮换 facilitator | 评审方（负责人 / 委员会），有 Decider |
| 产出 | 洞察与改进点 | 决策记录 + 待办 |
| 危险 | 聊得热闹无结论 | 变成领导拍板会，同伴不敢提问题 |

**把两者混在一个会里，结果是"既没改进也没结论"。** 中文团队最常见的失败：名为评审会，实为汇报会 ——  presenter 逐页讲，下面只点头。要拆就拆成两场，或同一场先 critique（前半段禁决策）再 review（后半段只决策）。

---

## 2. 评审前的三个前提（NN/g 原文三主题，必做）

1. **范围清晰**：这次评什么、不评什么，必须写死。范围不清的评审 100% 跑偏（有人评配色、有人评流程，互不挨着）。
2. **目标一致**：先对齐"要解决什么问题、给谁解决"。没有共识的目标，任何反馈都是主观偏好。
3. **对话而非指令**：`I would have done it differently`（"要是我就换个做法"）是评审杀手——它只表达立场，不给理由，逼作者辩护。换成"这个步骤让我犹豫，因为用户中途要回退两次"。

额外一条本技能立场：**材料提前 24h 发出**。当场才看稿 = 用前 5 分钟的第一印象下结论，严重度失真。

---

## 3. 给出反馈的七条铁律

1. **具体非模糊**：❌"按钮太大" → ✅"主行动按钮 48px 高、比次按钮大 1.6×，但低于 iOS 44pt 触控下限，建议对齐 44pt 并靠间距拉开层级"。
2. **挂在目标上**：先复述设计目标，反馈对得上才执行；对不上的是个人偏好，记录但不执行（见 §8）。
3. **分离品味与工艺（taste vs craft）**："我不喜欢这个蓝"是**品味**（记个人偏好）；"这个蓝在暗色下对比度 3.1:1，低于 WCAG 4.5:1"是**工艺**（必须改）。
4. **用行为化语言**：少说"用户会犹豫"，多说"把这个步骤从 3 步减到 1 步，减少中途流失"——后者可被验证。
5. **I like / I wish / I wonder**（LUMA/Gamestorming 的引导式反馈法）：
   - **like** = 肯定已经奏效的（不是客套，是锚定共识）；
   - **wish** = 一个具体可改进的点（带理由，非方案）；
   - **wonder** = 一个开放性探索问题（不要求当下回答，留作后续）。
6. **先肯定再建议（2 正 1 改配额）**：破冰用，强制每人先给 2 条做得好 + 1 条可改进；之后转自由讨论，否则容易只剩批评。
7. **给观察不给方案跳转**：先描述现象，让作者先想解法；除非被明确问"你建议怎么改"，否则别跳到"应该做成 X"。

> 红线：反馈针对**设计**，不针对**人**。"你这个设计"改成"这个方案"；"你没考虑无障碍"改成"这里还没看到键盘可达的路径"。

## 4. 接收反馈的四步（别辩护）

1. **不辩护**：辩解会吃掉真正讨论的时间。用"记下来"代替"但是"——哪怕你当场不同意，先落进清单，评审后逐个回应。
2. **追问到具体**：把"不太行"追问成"哪个环节让你不放心？""你预期用户会在这里做什么？"。模糊反馈不追问 = 拿回去瞎猜。
3. **归类**：每条反馈归到三类之一——**目标相关**（纳入）、**个人偏好**（记录不执行）、**已覆盖**（一句话说明即可，不重复讨论）。
4. **记录决策**：每条反馈 → 采纳 / 搁置 / 反驳，理由写进 ADR（§8）。没有处置结论的反馈 = 没发生的评审。

## 5. 怎么开一场评审（议程 / RACI / 远程异步）

### 5.1 RACI（handoff §9 讲的是角色动作，这里补权责）
- **R** Presenter：讲目标 → 讲故事（遇到什么问题、为什么这么决策）→ **明确想要哪类反馈**，快速讲完。
- **A** Decider：唯一拍板人。没 Decider 的评审 = 委员会人人可否决 = 设计 by committee（§7）。
- **C** Critiquer：跨职能（含开发、测试、运营）。开发早进场能在"改起来还便宜"时提可行性。
- **I** Facilitator：确保规则（三前提、禁方案跳转、计时），不产出内容。

### 5.2 远程与异步
- **同步远程**：共享屏幕 + 静音纪律；critique 阶段全员开麦，review 阶段只 Decider 说话。
- **异步评审**（分布式团队首选）：Figma 注释 + 录屏 walkthrough（讲清目标与卡点）+ **48 小时反馈窗口** + 截止后 Presenter 汇总 ADR。异步的好处：反馈者能深思，不被会场气氛裹挟；坏处：收敛慢，必须有硬截止。

### 5.3 时长铁律
- 单场 ≤ 45 分钟；超过就拆。注意力在第 30 分钟后断崖。
- 一份稿子最多评审 2 个独立模块，否则每个都只聊表面。

## 6. 评判框架（把"好不好"变成可讨论的尺子）

### 6.1 NN/g 10 可用性启发式（当作 critique 检查表）
1. 系统状态可见（反馈及时）
2. 系统与真实世界匹配（用语用户懂）
3. 用户控制与自由（撤销/重做）
4. 一致性与标准（别自创范式）
5. 防错优于报错
6. 识别优于回忆（别让用户背）
7. 灵活高效（快捷键/默认值）
8. 审美且极简（无关元素删掉）
9. 帮助用户识别、诊断、从错误恢复
10. 帮助与文档（必要时有）

评审时逐条过一遍，命中哪条就挂哪条——把"感觉不对"翻译成"违反启发式 #4"。

### 6.2 严重度评级（Nielsen 0–4）
- **0** 不值得改（锦上添花）
- **1**  cosmetic，不影响任务
- **2**  小问题，偶发卡顿
- **3**  严重，多数用户受阻
- **4**  灾难，任务无法完成
只有 **≥3** 进本轮必改清单；0–2 进 backlog，避免评审会变成挑刺大会。

### 6.3 DFV 三问（Desirability / Feasibility / Viability）
- **可取性**：用户想要吗？（情感/动机）
- **可行性**：技术做得出吗？（开发可行性）
- **可行性**：商业成立吗？（成本/收益）
三票各一票，缺任一票都是风险，必须在 ADR 写清"如何补票"。

### 6.4 双轴：重要性 × 确定性能
高重要 + 低确定 → **先验证再定**（做原型/AB），别在评审桌上靠辩论定生死。低重要无论确定与否 → 放权给执行者。

### 6.5 可取性测试（desirability testing）
用语词配对（给一组形容词让用户选）测情感共鸣，区分"好看"和"想要"——好看不等于想要，评审常把两者混为一谈。

## 7. 反模式 15 条

1. **design by committee（设计委员会化 / 委员会改稿）**：人人能改、无人负责，结果最安全的平庸方案；评审无 Decider 时必然滑向这里。
2. **HiPPO**（Highest Paid Person's Opinion，最高薪者意见）：薪资最高的人一开口，其他人闭嘴；用数据/启发式反驳，而非职位。
3. **审美化争论**：用"我觉得不好看"代替证据；要求"挂目标或挂启发式"。
4. **方案跳转**：没搞清问题就甩"应该做成 X"；先问"你看到的现象是什么"。
5. **模糊反馈**："不太行""再调调"——不追问到具体就不算反馈。
6. **迟到材料**：当场才发稿，靠第一印象下结论。
7. **现场改稿**：评审是发现问题，不是白板改稿；改稿留到会后。
8. **人身化**："你这个设计"——针对人，引发防御。
9. **只批评不肯定**：没有 like，作者进入防御态，听不进 wish。
10. **一言堂 / 沉默**：facilitator 没破冰，资深者说完就定。
11. **目标漂移**：评着评着忘了评什么，被一个细节带跑全场。
12. **决策不留痕**：会开完没 ADR，两周后被推翻重来。
13. **把偏好当需求**："我喜欢居中"当成用户需求写进 spec。
14. **用少数异议否决**：一个人强烈反对就推翻多数共识，且无数据支撑。
15. **评审变汇报**：Presenter 逐页讲、无人对话，时间耗尽无反馈。

## 8. 决策记录（ADR / critique notes）

### 8.1 ADR 模板（Architecture/Decision Record 套路借用到设计）
```
# ADR-<编号> <主题>
## 背景
  评审中争议点 + 涉及的相关目标/启发式
## 决策
  最终怎么定
## 备选
  被否决的方案 + 否决理由
## 后果
  已知权衡 / 待验证项
## 状态
  采纳 / 搁置 / 待验证（负责人 / 截止）
```

### 8.2 critique notes（问题行）
| 反馈 | 严重度(0–4) | 归类(目标/偏好/已覆盖) | 处置 | 负责人 | 截止 |
|---|---|---|---|---|---|
| … | 3 | 目标相关 | 采纳 | 甲 | 11-14 |

**铁律**：没有处置结论的反馈行 = 这条反馈没发生。

## 9. 工具

- **Figma comments**：原地注释 + 解决状态，异步评审主力。
- **Figjam**：critique 墙，贴 like/wish/wonder 便利贴。
- **Notion / 文档**：ADR 与 critique notes 沉淀，跨评审可追溯。
- **GitHub PR review（类比）**：diff（改了什么）/ comment（行内反馈）/ approve（决策）。把设计稿当 PR 看，反馈粒度更清晰。
- **Loom / 录屏**：walkthrough 讲目标与卡点，异步反馈的上下文来源。

## 10. 自检 20 项（评审前 / 中 / 后）

前（材料）：
1. 范围声明写了吗？评什么/不评什么。
2. 目标声明写了吗？给谁、解决什么。
3. 材料提前 24h 发出去了吗。
4. Decider 明确了吗（不是委员会）。
5. 参与角色跨职能了吗（含开发/测试）。

中（过程）：
6. 先复述目标再给反馈了吗。
7. 反馈具体、挂目标、带理由了吗。
8. 区分了品味与工艺吗。
9. 用了 like/wish/wonder 或 2 正 1 改吗。
10. 有人方案跳转时被拉回"先描述现象"了吗。
11. 针对设计不针对人了吗。
12. 模糊反馈被追问到具体了吗。
13. 时间 ≤ 45 分钟、模块 ≤ 2 个吗。
14. facilitator 守规则了吗（禁汇报、禁一言堂）。

后（产出）：
15. 每条反馈归类了吗（目标/偏好/已覆盖）。
16. 严重度 0–4 标了吗，≥3 进必改吗。
17. 有没有逐条过 NN/g 10 启发式。
18. DFV 三票都考虑了，缺票写补票计划了吗。
19. ADR / critique notes 写了吗，每条有处置+负责人+截止吗。
20. 异步评审有 48h 硬截止并汇总了吗。

## 11. 可抄模板（4 段）

### 11.1 反馈话术清单（给反馈的人照着说）
```
- like：这一屏把主行动放最右、层级清楚，一眼知道点哪。
- wish：注册这步要填 5 项，可否先收邮箱、其余进尾流程？
       （理由：启发式 #7 灵活高效，转化漏斗会少一截）
- wonder：如果用户用键盘全程操作，这一步的焦点顺序顺吗？
- 追问模板：你预期用户在这里会做什么？哪个环节让你不放心？
```

### 11.2 评审议程（45 分钟）
```
00–05   facilitator 重申范围+目标+Decider
05–10   presenter 讲目标与故事（不辩护、快速）
10–30   critique：like/wish/wonder，禁决策
30–40   review：Decider 对 ≥3 问题拍板
40–45   汇总 ADR / critique notes，定负责人+截止
```

### 11.3 ADR 片段
```
# ADR-014 注册流程是否分步
## 背景  评审争议：5 项一次性填 vs 先邮箱后补全
## 决策  先邮箱（首屏 1 项），其余进激活后尾流程
## 备选  一次性填——否决：启发式 #7，转化漏斗流失风险
## 后果  需补"激活后补全"引导页；待验证首登转化
## 状态  采纳（甲 / 11-14 出原型）
```

### 11.4 异步评审 checklist
```
[ ] 材料 + 目标 + 范围声明已发
[ ] 附 walkthrough 录屏（≤3 分钟）
[ ] 反馈窗口 48h，截止时间写死
[ ] 用 Figma comment，行内挂目标
[ ] 截止后 Presenter 汇总 ADR，Decider 确认
```
